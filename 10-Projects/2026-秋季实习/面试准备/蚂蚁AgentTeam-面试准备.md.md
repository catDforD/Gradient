**2. 从用户提交需求到工具执行、结果返回，完整链路是什么？CLI 与 Web 如何复用同一个执行核心？**
我一般使用 web 端配置和操作，web 通过 ws 发送命令 server 解析，然后进入 runtime 准备执行环境，组装上下文信息，装配内置工具，MCP 和调用 subagent 工具，估算上下文长度，必要时压缩历史。

然后进到 agent core 部分，这部分会发起模型调用（内容包含系统提示词、历史消息，Hook 附加的上下文和当前用户输入，工具定义），然后将模型返回结果转化成各种信息（文本信息、思维链，工具调用或者结束标志），在 runtime 持续运行的同时也会负责将收到的内容事件外发，这样 CLI 和 web 能够快速消费。

当 agent 有工具调用的时候，core 部分负责发起工具调用，内部附带一些权限检查（此处可能需要用户审批，会由 runtime 负责向上向用户获取决定再交还给 core 部分，返回结果即为 执行成功或失败、等待审批），目前工具只有搜索读取类工具可以并发，最多 4 个并发工具，写类工具 和 shell 工具只能串行。工具结果会回灌 core 循环往复直到完成这一轮。结果会在执行给过程中持续返回并更新会话内容。

以上所有执行期间的内容都会记录转化为 session facts（持久化消息内容），这些内容都是重建后续上下文的唯一来源。

CLI 和 web 都统一调用 runtime 这个核心会话编排，两端主要不同在于处理输入输出、展示输出内容稍有不同。


**3. 多 Agent 如何划分职责、表达任务依赖？同时修改同一份代码怎么办？什么时候单 Agent 反而更合适？**
当前核心是主 agent 分派任务，子 Agent 保留各自的对话，共享一个工作空间。Agent 职责分为 4 类，即 explore、plan、worker 和 reviewer 四个职责。任务依赖是通过主 agent 调用顺序表达，目前没有设计固定的任务图。主 agent 调用 subagent 的方式为 delegate_task 和 spawn_subagent ，delegate_task 负责临时指派调查任务，每个主 agent 最高同时可以启动 4 个 delegate_task 任务。spawn_subagent 则是持久化后台实例，通过（inspect、wait、send、cancel）来管理各个实例，最多 8 个实例同时 4 并发运行。

关于修改同一份代码，我限制不可以同时进行文件修改和 shell 操作， worker 才能拥有写入权限，其它 worker 都需要排队。总之就是只有一个空闲许可， worker 拿到许可才能进行文件修改或者 shell 操作，主 agent 也需要这个许可才能操作。
		
单 agent 更适合任务短、依赖紧密共享上下文多的情况，例如修一个 bug、调个参数、每一步工作都紧密衔接的工作类型、或者修改集中在同一文件、位置或者接口的情况。

**4. 上下文压缩什么时候触发？哪些内容可以概括，哪些任务约束、执行状态必须保留？**
上下文压缩是根据模型上下文窗口来计算的，一般是当前会话上下文到达阈值（0.935）即触发自动压缩，用户也可以自己手动触发压缩。在新一轮任务执行前，会在 runtime 组装上下文后估算输入 token 然后判断是否需要压缩上下文。

在实际压缩的时候用七个固定部分来承接历史消息：用户目标与约束、重要决策、文件与代码状态、命令结果与错误、当前进度、待办、开放问题。摘要提示词会要求在上述框架下压缩信息。其中压缩最大的内容是应该是文件读取、搜索结果、命令输出等内容，这些直接读取到的内容都会被处理成结论和相关事实以压缩上下文空间。


**5. 权限审批在哪里生效？是提示模型“不要执行”，还是程序真正阻止执行？拒绝、超时后怎么办？**
权限审批的请求一般是在 runtime 发起的，工具内部权限分为三类：执行、拒绝和挂起等待审批。真正阻断的点可以这么看，内置工具会在工具调用执行前审查权限，这个一般是写在工具内部的（自己写的 apply patch，edit 等工具）。对于 MCP 工具则是在发送 tool call 之前审批权限。shell 则是启动进程前审批权限，也是写在工具内部的。

用户拒绝后一般记录审批拒绝，返回工具执行拒绝错误，继续处理其它调用允许模型决定后续行动等等。工具超时后按工具超时处理，和审批无关，该返回错误就返回错误，该返回超时就返回超时。不过审批超时还没处理，一般处理思路是默认拒绝，然后返回超时错误提示给模型即可。


**6. 验收 Hook 具体检查什么？如果 Agent 宣布完成，但测试失败，系统如何继续或停止？**
验收 Hook 检查本轮结束，主要能够拿到模型最终回答，工具调用信息和本地的一些配置信息，检查什么由 Hook 命令决定。比如示例测试就是运行当前仓库测试用例，成功返回 complete，失败返回 continue。如果测试失败，Hook 会返回 `continue` 并带上对应的反馈信息重新调用模型继续行动，如果 Hook 返回失败则把本轮标记为失败并终止，不过返回失败是可以编写的规则，具体看当前 Hook 是怎么写的。

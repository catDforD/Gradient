## 上下文窗口与遗忘

- **如何解决上下文过长导致的遗忘问题？**（🔥）—— 压缩摘要、分层记忆、检索式召回、滑动窗口。出处：[[20-Areas/实习与求职/面试题与经验/AI-Agent与大模型岗位面经汇总-01至05-07-08|汇总A·面经02]]、[[20-Areas/实习与求职/面试题与经验/AI-Agent与大模型岗位面经汇总-01至05-07-08|汇总A·面经05]]
  > [!success]- ✅ AI 解答 · Q06 · 2026-09-15
  > **🎯 标准答案（面试版）**主流解法是『压缩+外置』组合：①滑动窗口，只保留最近 N 轮完整对话；②对更早历史做摘要压缩（compaction，如 Claude Code 的 auto-compact），保留任务目标、关键结论与未完成事项；③把需要长期保留的信息外置到记忆系统（向量库/文件），用时检索召回；④把核心约束固化到系统提示或状态文件中常驻。
  > **📌 要点**
  > - 窗口+摘要分层：近看原文，远看摘要
  > - 检索式召回：对话历史也做 RAG
  > - 关键信息『钉』在高注意力位置（头尾）
  > - 摘要有损得聪明：目标/结论/待办必须保留
  > **🔬 原理深入**
  > 遗忘有两个来源：窗口物理容量不够，以及 lost-in-the-middle 现象（Liu et al., 2023：长上下文中部信息利用率显著下降）——所以不只是『塞得下』的问题，还要把关键信息放在头尾等高注意力区域。摘要必然有损，工程上要显式定义哪些信息允许丢失。
  > **🔗 延伸**
  > 可聊 KV cache 复用与成本、分层记忆架构（工作/情景/语义记忆）。

  > [!success]- ✅ AI 解答 · Q06 · 2026-09-30（复习轮）
  > **🎯 标准答案（面试版）** 解决上下文遗忘有四板斧：①滑动窗口截断最近 N 轮；②历史压缩摘要（auto-compact，超阈值触发把旧对话折叠成摘要）；③外置记忆检索式召回（把历史/知识放向量库，按需注入）；④关键约束固化到系统提示常驻。同时要利用 lost-in-the-middle 规律——模型对头尾内容注意力高，关键信息放首尾。
  > **📌 要点**
  > - 压缩时机：按 Token 阈值触发而非固定轮数；摘要要保留约束、决策、未完成事项
  > - 截断的陷阱：早期对话里的安全约束、任务目标会被丢掉——所以硬约束必须常驻 system prompt，历史只是素材
  > - 检索式召回的粒度：按轮次还是按语义块，直接影响召回噪声
  > **🔬 原理深入** 遗忘的根源是注意力分配：上下文越长，单条信息的注意力被稀释，且位置有头尾偏置（lost-in-the-middle，Liu et al. 2023）。所以本质不是"记得多"而是"该在场的在场"——把信息按重要性分层：常驻层（system prompt）、工作层（窗口）、归档层（外置检索）。KV cache 复用与窗口截断天然矛盾：截断即失效前缀缓存，成本要一起算。
  > **🔗 延伸** 可聊分层记忆架构（工作记忆/情景记忆/语义记忆）与 Anthropic 的 context compaction 实践。

  > **📌 要点**
  > - 摘要质量可测：用摘要后上下文让模型复述目标与约束，复述不全说明摘要丢了关键信息
  > - 截断顺序有讲究：先丢工具原始返回（可重取）、再丢寒暄，最后才动决策与约束
  > - 检索式召回要控噪：条数上限 + 相关性阈值，宁缺毋滥
  > **🔬 原理深入** 遗忘有两层原因要分开治：物理容量（靠压缩与外置）和注意力分配（靠布局，头尾优先）。延伸一点：KV cache 命中依赖前缀稳定，频繁压缩与重排会牺牲缓存收益，因此压缩粒度应与缓存策略联合设计。

  > **🎯 标准答案（面试版）** 把上下文组装当服务治理来答：定义 SLO 指标（首 token 延迟、prefix cache 命中率、压缩触发率、超窗拒绝率），按并发会话数×平均 token 做容量规划；新策略按会话灰度分流，异常时熔断到保守模式（强制摘要 + 截断历史）并告警。这样上下文管理从「调参」变成「可观测、可回滚的工程系统」。

- **多个 Agent 如何处理输入？动态上下文使用什么数据结构？** —— 消息队列/黑板/状态树。出处：[[20-Areas/实习与求职/面试题与经验/AI-Agent与大模型岗位面经汇总-01至05-07-08|汇总A·面经04]]
  > [!success]- ✅ AI 解答 · Q71 · 2026-09-22
  > **🎯 标准答案（面试版）** 多 Agent 的输入分发常见三类数据结构：**消息队列**（Agent 间异步事件驱动，解耦削峰，适合流水线长任务）、**黑板模式**（中央共享工作区，各 Agent 增量读写、互相激发，适合协作求解）、**状态树/图**（如 LangGraph 的 State，按通道组织字段，节点返回部分更新、reducer 决定合并语义）。选型核心看耦合度与实时性：需要即时反馈的循环用共享 State，跨服务长任务用消息队列。
  > **📌 要点**
  > - 消息队列：事件驱动、解耦、可回放，但延迟高、不适合紧耦合循环
  > - 黑板模式：多专家对同一问题增量作答，控制权在调度器
  > - 状态树：LangGraph State 通道化读写，append/overwrite 语义明确
  > - 关键设计点：写冲突与可见性——append-only 最安全，覆盖需谨慎
  > **🔬 原理深入** LangGraph 的 State 本质是「带 reducer 的通道」：每个节点返回 partial update，reducer（append/overwrite/自定义合并）决定多节点并行写同一 key 时的行为，天然规避互踩。多 Agent 上下文设计的第一性问题是**写冲突**与**可见性边界**：谁能看到谁的生产物、覆盖语义是什么。工程上还须隔离「共享黑板」与「私有 scratchpad」，防止 Agent 间上下文互相污染、注意力被无关内容稀释。
  > **🔗 延伸** 与题库中「多 Agent 分工与上下文共享」题呼应；可延伸 LangGraph Supervisor/Swarm、A2A 协议与 MCP 在多 Agent 通信中的角色。

  > [!success]- ✅ AI 解答 · Q71 · 2026-10-09（复习轮）
  > **🎯 标准答案（面试版）** 多 Agent 输入分发的选型可以压缩成三问：**要实时吗**（紧耦合循环→共享 State）、**要吞吐吗**（长任务流水线→消息队列）、**要多视角协作吗**（专家会诊→黑板）。2026 年的新变化是把「通信协议」从自研里解放出来：Agent 间用 **A2A**（Agent-to-Agent）声明能力与任务卡，工具面统一走 MCP，自研只剩编排语义。另一个工程共识是**事件溯源式上下文**：所有 Agent 产出以不可变事件追加，视图（黑板/State）只是事件的物化投影，天然获得可回放与审计能力。
  > **📌 要点**
  > - 选型三问口诀：实时性→State、吞吐→队列、多视角→黑板
  > - 事件溯源：上下文=不可变事件流，黑板/State 只是物化视图，可回放可审计

  > [!success]- ✅ AI 解答 · Q71 · 2026-10-24（复习轮 R3）
  > **🎯 标准答案（面试版）** 并发写才是这道题的真难点。三种协议按可靠性排序：**单写者模型**（每个状态分区只有一个 owner/actor，串行化写入，最稳）、**乐观并发**（带版本号 CAS，冲突则重读重试，重试上限 2~3 次）、**CRDT/append-only**（各自追加、按确定规则合并，天然无冲突但语义受限）。输入分发侧还要处理三类故障：重复投递（消息 ID + 幂等消费表）、乱序（单调 sequence 号 + 窗口重排）、丢失（至少一次 + ACK/重放）。
  > **📌 要点**
  > - 单写者 > CAS > CRDT：按「一致性要求 × 实现成本」选
  > - 幂等键 = 消息 ID + 消费者 ID，去重表设 TTL
  > - 容量估算：每 Agent 一个 topic/分区，分区数按峰值 QPS 定；共享 State 走内存（微秒级），跨服务走队列（百毫秒级）
  > - 背压必须有：队列水位告警 + 消费者限流，否则雪崩
  > **🔬 原理深入** Actor 模型把「并发」变成「串行消息处理」，从根上消灭写冲突；CAS 依赖硬件原子指令与重试，适合热点分散的场景；append-only 则把冲突推迟到读时合并（reducer 必须幂等，否则重放会翻倍）。工程上最常被追问的是「重试导致重复执行」：答案是把副作用做成幂等操作（upsert 而非 insert、状态机只允许合法迁移）。
  > **🔗 延伸** 追问：十万级 Agent 消息怎么扩？答分层 topic + 采样监控 + 按业务域分片；与「多 Agent 上下文共享」题可组合成完整答案。
- **多轮对话的上下文记忆如何实现？** —— 会话级 State + 持久化存储 + 注入策略。出处：[[20-Areas/实习与求职/面试题与经验/AI-Agent开发岗位面经汇总-2026年4月-01至07|汇总B·面经02]]
  > [!success]- ✅ AI 解答 · Q72 · 2026-09-22
  > **🎯 标准答案（面试版）** 多轮对话记忆分三层：① **会话级短期记忆**=运行时消息窗口/State，本次对话内有效；② **跨会话长期记忆**=持久化存储（向量库存语义、KV/文件存事实偏好、数据库存结构化事实），按用户/会话 ID 组织；③ **注入策略**=每次请求按相关性+预算把长期记忆检索出来放进上下文。写入要筛选（不是什么都存），读取要排序（相关性×时效）。
  > **📌 要点**
  > - 短期：messages 窗口 + 摘要压缩防溢出
  > - 长期：向量库（语义相似）、KV/文件（事实偏好）、DB（结构化）
  > - 注入：top-k 检索 + 重排，置于 system 或消息前缀
  > - 用户画像类与任务过程类记忆分开管理
  > - 代表实现：mem0、Letta（MemGPT）、LangGraph Store
  > **🔬 原理深入** 经典思想是 MemGPT/Letta 的「LLM 即操作系统」：主上下文=内存，外部库=磁盘，模型自己调用工具把记忆换页进出（page in/out）。工程难点在**写入筛选**——无差别存储会让记忆库被噪音淹没、检索精度随规模下降，常用显著性打分+实体去重合并。**注入位置**也影响效果：稳定偏好放 system（长期有效），临时事实放消息序列（会话结束即弃）。

## Prompt / Context / Harness 工程 🔥

- **Prompt 工程、Context 工程和 Harness 工程的区别是什么？**（🔥，概念边界必背）—— Prompt 是单次输入内容，Context 是模型可见全部信息的管理，Harness 是执行护栏与运行时。出处：[[20-Areas/实习与求职/面试题与经验/AI-Agent与大模型岗位面经汇总-01至05-07-08|汇总A·面经04]]，相关概念笔记 [[30-Resources/AI/Agent/长时运行 Agent 的有效 Harness]]

  > **🎯 标准答案（面试版）**三者是逐层放大的关系。Prompt 工程关注单次调用里『怎么说』：指令措辞、few-shot、输出格式；Context 工程关注每次调用『模型能看到什么』：系统提示、工具定义与返回结果、检索内容、历史与状态的组装与取舍，本质是在有限窗口内做信息预算；Harness 工程关注模型外围的运行时：Agent 循环、工具执行、重试与降级、权限护栏、评估与监控。即 Prompt ⊂ Context ⊂ Harness。
  > **📌 要点**
  > - Prompt = 一次调用的输入文本
  > - Context = 模型可见的全部信息的管理
  > - Harness = 执行护栏与运行时，决定失败语义
  > **🔬 原理深入**
  > 只优化 Prompt 的收益有天花板，因为失败往往源于『模型没看到关键信息』（Context 问题）或『出错后没有纠错回路』（Harness 问题）。Context 工程把信息当稀缺资源做预算分配；Harness 决定长时运行 Agent 的可靠性上限——重试、熔断、审计都在这一层。

  > - 基线先行：没有基线就没有「更简洁」，先采一周 PR 中位行数/复杂度/重复率
  > - 四道门禁：spec → 生成单元上限 → CI 静态闸门 → 小步 PR + 可回滚
  > - 反例：只调 prompt 不加门禁，换个模型版本立刻回退
  > - 数字示例：PR 中位行数 400→180、重复率 8%→2%、评审返工次数 -40%
  > **🔬 原理深入** 冗长是「局部最优」的必然产物——模型看不到仓库全貌，只能用防御性代码堆安全感。门禁把仓库级约束编码成机器可判规则，等于给模型补上缺失的全局上下文。约束必须机器可判：「简洁」不可判，「函数 ≤ 50 行、不得重复已有 util」可判，可判才能进流水线自动拒绝。
  > **🔗 延伸** 追问：模型不遵守 spec 怎么办？→ 由 CI 拒绝合并，而不是反复提醒模型；约束应由流水线执行，不依赖模型自觉。

## 幻觉与可靠性

- **幻觉问题如何解决？**（🔥）—— RAG 注入事实、引用溯源、温度与输出约束、事后校验。出处：[[20-Areas/实习与求职/面试题与经验/AI-Agent与大模型岗位面经汇总-01至05-07-08|汇总A·面经05]]、[[20-Areas/实习与求职/面试题与经验/AI-Agent开发岗位面经汇总-2026年4月-01至07|汇总B·面经05]]
  > [!success]- ✅ AI 解答 · Q09 · 2026-09-15
  > **🎯 标准答案（面试版）**工程上以『接地+校验』为主线：①RAG 注入可核实的事实，并要求每个论断给出引用；②把『回答不知道』设计为合法输出（cite-or-abstain）；③事实型任务降低温度、用结构化输出约束格式；④增加事后校验：另一个模型/规则引擎审查，或用工具验证（计算器、代码执行）；⑤高风险场景用一致性采样（SelfCheckGPT 思路）检测可疑输出。模型侧靠事实性微调与 RLHF 缓解。
  > **📌 要点**
  > - RAG + 引用溯源是第一道防线
  > - 弃答合法化比强行回答更工程化
  > - 生成与验证分离，论断绑定证据
  > - 目标不是零幻觉，而是幻觉可被发现
  > **🔬 原理深入**
  > 幻觉的根源是模型按最大似然『补全』文本而非查证事实——训练目标是说得像而非说得对，因此无法根除，只能做系统级防御。实践中检索质量对事实性的影响常大于模型尺寸；Agent 场景里工具返回值是天然接地源。
  > **🔗 延伸**
  > 可聊评估指标（faithfulness、answer relevance）、LLM-as-judge 做自动化事实核查的局限。

  > [!success]- ✅ AI 解答 · Q09 · 2026-09-30（复习轮）
  > **🎯 标准答案（面试版）** 幻觉治理是分层的：事前——RAG 注入事实让模型"开卷答题"，并强制引用溯源（每个结论挂来源）；事中——低温采样、结构化输出约束、cite-or-abstain（提示词里显式允许"不知道/证据不足"）；事后——校验链：规则校验（格式/数值）、工具验证（代码执行、检索比对）、LLM-as-judge 审查、一致性采样（多次生成投票）。目标不是零幻觉，而是幻觉可被发现、可归因。
  > **📌 要点**
  > - 幻觉根源：next-token 预测优化的是"像"不是"对"；参数化知识过时且有压缩损失
  > - cite-or-abstain 是性价比最高的单点改造：给模型"拒答"的合法出口，编造率显著下降
  > - RAG 不是银弹：检索错了会引入新的幻觉源，检索质量是前置条件
  > **🔬 原理深入** RAG 改变的是条件分布——把闭卷考变开卷考，模型只需从给定材料归纳而不是凭参数回忆。但要注意归因链：答案错可能是生成错，也可能是检索错，排障要分段（先看检索命中质量，再查生成忠实度），这也是 RAG 评估分 retrieval metrics 和 faithfulness 两组的原因。
  > **🔗 延伸** 可聊 RAG 三元组评估指标（faithfulness/answer relevance/context precision）与 LLM-as-judge 的偏差（位置偏差、自我偏好）。

  > [!success]- ✅ AI 解答 · Q09 · 2026-10-17（复习轮 R3）
  > **🎯 标准答案（面试版）** 第三轮强调『分层 + 归因』：事前接地（RAG + 强制引用）、事中约束（低温、结构化输出、cite-or-abstain）、事后校验（规则、工具执行、一致性采样）。排障必须分段归因——先查检索命中与排序质量，再查生成忠实度，否则容易把检索错判成生成错。
  > **📌 要点**
  > - 三层防线各管一段：检索质量、生成忠实度、输出可用性
  > - 指标可观测：faithfulness / answer relevance / context precision 与 recall 分指标定位
  > - 高风险输出走双通道：模型生成 + 规则或工具复核，一致才放行
  > **🔬 原理深入** 幻觉无法根除，因为训练目标优化的是『像不像』而非『对不对』，参数化知识必然有压缩损失与时效滞后。工程目标因此调整为：让幻觉可被发现、可被拦截、影响可控。工具型 Agent 有天然优势——工具返回值是接地源，比参数记忆可靠得多。
  > **🔗 延伸** 可聊 LLM-as-judge 的偏差（位置、自我偏好）与做事实核查的边界，以及 RAG 三元组指标在 CI 里的阈值设计。
- **AI 的局限性和不可靠性，遇到问题如何解决？** —— 兜底策略、人工介入、评测驱动。出处：[[20-Areas/实习与求职/面试题与经验/AI-Agent与大模型岗位面经汇总-01至05-07-08|汇总A·面经05]]
  > [!success]- ✅ AI 解答 · Q82 · 2026-09-23
  > **🎯 标准答案（面试版）**：承认 LLM 存在幻觉与输出不确定，无法根除只能工程化管理。做法是三层兜底：关键路径保留人工介入（human-in-the-loop），高危操作强制确认；用评测集持续驱动质量（eval-driven），badcase 回流防劣化；对不可靠输出做冗余设计——多次采样投票、双模型交叉校验、低置信度自动降级到规则或人工。
  > **📌 要点**
  > - 兜底策略：超时/异常/低置信度 → 降级规则引擎或转人工
  > - 人工介入：删库、支付等高危动作强制 human-in-the-loop，最小权限控爆炸半径
  > - 评测驱动：golden set 回归 + 幻觉率/准确率指标，发版前后对比防劣化
  > - 冗余校验：self-consistency 多数投票、verifier 模型复核、引用溯源
  > - 可观测：全链路 trace + 日志留存，问题可定位可回放
  > **🔬 原理深入**：LLM 的不可靠性来自概率采样与训练数据覆盖缺口，属于模型本性而非工程缺陷，因此「解决」的准确定义是让不可靠性可度量、可拦截。离线侧把幻觉率变成数字：构建真实 badcase 评测集，每次改 prompt/换模型都跑回归；在线侧用 self-consistency（同一问题多次采样取多数一致答案）与 verifier 二次审查提升精度。权限上遵循最小化原则——只给模型完成任务必需的工具与数据，即使幻觉触发了危险调用，影响面也被限制住。
  > **🔗 延伸**：常见追问：评测集怎么建？（线上 badcase 持续沉淀 + 定期人工扩充）线上如何发现幻觉？（强制引用溯源 + 用户反馈闭环打标）

  > [!success]- ✅ AI 解答 · Q82 · 2026-10-10（复习轮）
  > **🎯 标准答案（面试版）** 答题先分类再治理：不可靠分三类——事实错（幻觉）、执行错（工具误用/越权）、边界不清（歧义），三类防线不同。再按风险分级：只读操作自动执行、写操作确认、破坏性操作双人复核，把「爆炸半径」当第一性设计。最后用运营指标闭环：人工介入率、幻觉率、任务成功率三条曲线随版本迭代。
  > **📌 要点**
  > - 风险分级矩阵：读/写/破坏性 × 自动/确认/复核，权限最小化兜底
  > - 灰度与回滚：新 prompt/新模型先小流量跑，指标劣化自动回滚
  > - 人工介入率是成本指标（成熟体系常压在个位数百分比），不是越低越好——高危场景宁可多留
  > - 可观测三件套：全链路 trace、工具调用日志、失败样本自动归档成评测集
  > **🔬 原理深入** 兜底的本质是把「不确定性」转成「可度量 + 可拦截」：离线用评测集度量，在线用分级拦截。要注意一个反直觉点——兜底不是越严越好，过度确认会让 agent 变得没用（用户绕过流程），所以分级的边界要用真实误伤率来校准，而不是拍脑袋。
  > **🔗 延伸** 追问：怎么防止评测集过拟合？→ 线上 badcase 持续回流 + 定期换血 + 留出未见过的 holdout 集。

  > [!success]- ✅ AI 解答 · Q82 · 2026-10-25（复习轮 R3）
  > **🎯 标准答案（面试版）** 用一次真实事故的时间线讲最有说服力：模型把测试环境的批量操作跑到了生产，缺二次确认与权限边界。复盘出三层防线：事前风险分级（读/写/破坏性 × 自动/确认/复核）、事中熔断（工具错误率与超时率超阈值自动停）、事后可回滚（幂等 + 审计 + 一键回滚脚本）。再用混沌演练验证：注入超时、429、脏数据、格式错误，看防线是否真的拦住。
  > **📌 要点**
  > - 风险分级矩阵要落成配置，而不是写在文档里
  > - 熔断三指标：工具错误率、任务超时率、人工接管率
  > - 演练清单：超时、限流、工具返回脏数据、模型输出格式错误
  > - 事故复盘的产出必须是「门禁/配置变更」，而不是「下次注意」
  > **🔬 原理深入** 兜底体系的价值不在正常路径，而在异常路径被真正触发时的表现。混沌演练把「我们以为有兜底」变成「我们验证过兜底」；没有演练的熔断配置，大概率在真实故障时因阈值不合理而失灵。另一个反直觉点：兜底不是越严越好，过度确认会让 Agent 变得没用，用户会绕过流程——边界要用真实误伤率校准。
  > **🔗 延伸** 追问：怎么衡量兜底成本？→ 人工介入率 × 单次成本 + 误伤导致的业务损失，与事故损失做对比，用数字决定分级阈值。

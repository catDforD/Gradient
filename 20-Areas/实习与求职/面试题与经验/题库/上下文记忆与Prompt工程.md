# 上下文、记忆与 Prompt 工程

按知识类别整理的面试题库之四。题目从各面经抽取去重，🔥 表示在多份面经中重复出现（优先复习）。出处缩写见 [[20-Areas/实习与求职/面试题与经验/面试题与经验索引|索引]]。此类别在 5 份面经中全部出现，是必考主线。

## 上下文窗口与遗忘

- **如何解决上下文过长导致的遗忘问题？**（🔥）—— 压缩摘要、分层记忆、检索式召回、滑动窗口。出处：[[20-Areas/实习与求职/面试题与经验/AI-Agent与大模型岗位面经汇总-01至05-07-08|汇总A·面经02]]、[[20-Areas/实习与求职/面试题与经验/AI-Agent与大模型岗位面经汇总-01至05-07-08|汇总A·面经05]]
  > [!success]- ✅ AI 解答 · Q06 · 2026-09-15
  > **🎯 标准答案（面试版）**主流解法是『压缩+外置』组合：①滑动窗口，只保留最近 N 轮完整对话；②对更早历史做摘要压缩（compaction，如 Claude Code 的 auto-compact），保留任务目标、关键结论与未完成事项；③把需要长期保留的信息外置到记忆系统（向量库/文件），用时检索召回；④把核心约束固化到系统提示或状态文件中常驻。
  > **📌 要点**
  > - 窗口+摘要分层：近看原文，远看摘要
  > - 检索式召回：对话历史也做 RAG
  > - 关键信息『钉』在高注意力位置（头尾）
  > - 摘要有损得聪明：目标/结论/待办必须保留
  > **🔬 原理深入**
  > 遗忘有两个来源：窗口物理容量不够，以及 lost-in-the-middle 现象（Liu et al., 2023：长上下文中部信息利用率显著下降）——所以不只是『塞得下』的问题，还要把关键信息放在头尾等高注意力区域。摘要必然有损，工程上要显式定义哪些信息允许丢失。
  > **🔗 延伸**
  > 可聊 KV cache 复用与成本、分层记忆架构（工作/情景/语义记忆）。
- **工程中如何处理上下文？** —— 结合自己项目讲上下文组装策略。出处：[[20-Areas/实习与求职/面试题与经验/AI-Agent与大模型岗位面经汇总-01至05-07-08|汇总A·面经04]]

  > [!success]- ✅ AI 解答 · Q70 · 2026-09-21
  > **🎯 标准答案（面试版）** 工程上按「预算分配 → 组装 → 压缩 → 持久化」四步处理上下文：先给系统提示、few-shot、历史对话、工具结果分别设 token 配额；再按「稳定内容在前、易变内容在后」组装（对 prefix cache 友好）；超出预算时做滑动窗口裁剪或历史摘要压缩；跨会话关键事实沉淀到外部记忆库（向量库/文件），按需检索注入。
  > **📌 要点**
  > - 预算制：各上下文分区设 token 上限，超限有明确的降级顺序
  > - 组装顺序：system → 长期记忆 → few-shot → 历史 → 当前输入；稳定前缀利于 KV cache 复用
  > - 历史管理：滑动窗口 + 摘要压缩（auto-compact）+ 关键信息抽取固化
  > - 工具结果裁剪：大结果落盘、回传摘要与引用路径，防止单轮撑爆
  > **🔬 原理深入** 上下文组装质量决定注意力分配：lost-in-the-middle 现象下中段信息利用率显著偏低，关键约束应放头尾。追问：多轮 Agent 调用上下文膨胀怎么办？——只保留上一轮工具结果摘要、用结构化 State 代替原始消息流、按需重读文件而非常驻。记忆与上下文的边界：易变的进上下文，稳定的进外部记忆。
  > **🔗 延伸** 与 Q06（遗忘）、Q07（长短期记忆）联动复习；实测 prefix cache 命中率是成本优化抓手；Anthropic/OpenAI 的 context editing 实践。
- **多个 Agent 如何处理输入？动态上下文使用什么数据结构？** —— 消息队列/黑板/状态树。出处：[[20-Areas/实习与求职/面试题与经验/AI-Agent与大模型岗位面经汇总-01至05-07-08|汇总A·面经04]]
  > [!success]- ✅ AI 解答 · Q71 · 2026-09-22
  > **🎯 标准答案（面试版）** 多 Agent 的输入分发常见三类数据结构：**消息队列**（Agent 间异步事件驱动，解耦削峰，适合流水线长任务）、**黑板模式**（中央共享工作区，各 Agent 增量读写、互相激发，适合协作求解）、**状态树/图**（如 LangGraph 的 State，按通道组织字段，节点返回部分更新、reducer 决定合并语义）。选型核心看耦合度与实时性：需要即时反馈的循环用共享 State，跨服务长任务用消息队列。
  > **📌 要点**
  > - 消息队列：事件驱动、解耦、可回放，但延迟高、不适合紧耦合循环
  > - 黑板模式：多专家对同一问题增量作答，控制权在调度器
  > - 状态树：LangGraph State 通道化读写，append/overwrite 语义明确
  > - 关键设计点：写冲突与可见性——append-only 最安全，覆盖需谨慎
  > **🔬 原理深入** LangGraph 的 State 本质是「带 reducer 的通道」：每个节点返回 partial update，reducer（append/overwrite/自定义合并）决定多节点并行写同一 key 时的行为，天然规避互踩。多 Agent 上下文设计的第一性问题是**写冲突**与**可见性边界**：谁能看到谁的生产物、覆盖语义是什么。工程上还须隔离「共享黑板」与「私有 scratchpad」，防止 Agent 间上下文互相污染、注意力被无关内容稀释。
  > **🔗 延伸** 与题库中「多 Agent 分工与上下文共享」题呼应；可延伸 LangGraph Supervisor/Swarm、A2A 协议与 MCP 在多 Agent 通信中的角色。
- **多轮对话的上下文记忆如何实现？** —— 会话级 State + 持久化存储 + 注入策略。出处：[[20-Areas/实习与求职/面试题与经验/AI-Agent开发岗位面经汇总-2026年4月-01至07|汇总B·面经02]]
  > [!success]- ✅ AI 解答 · Q72 · 2026-09-22
  > **🎯 标准答案（面试版）** 多轮对话记忆分三层：① **会话级短期记忆**=运行时消息窗口/State，本次对话内有效；② **跨会话长期记忆**=持久化存储（向量库存语义、KV/文件存事实偏好、数据库存结构化事实），按用户/会话 ID 组织；③ **注入策略**=每次请求按相关性+预算把长期记忆检索出来放进上下文。写入要筛选（不是什么都存），读取要排序（相关性×时效）。
  > **📌 要点**
  > - 短期：messages 窗口 + 摘要压缩防溢出
  > - 长期：向量库（语义相似）、KV/文件（事实偏好）、DB（结构化）
  > - 注入：top-k 检索 + 重排，置于 system 或消息前缀
  > - 用户画像类与任务过程类记忆分开管理
  > - 代表实现：mem0、Letta（MemGPT）、LangGraph Store
  > **🔬 原理深入** 经典思想是 MemGPT/Letta 的「LLM 即操作系统」：主上下文=内存，外部库=磁盘，模型自己调用工具把记忆换页进出（page in/out）。工程难点在**写入筛选**——无差别存储会让记忆库被噪音淹没、检索精度随规模下降，常用显著性打分+实体去重合并。**注入位置**也影响效果：稳定偏好放 system（长期有效），临时事实放消息序列（会话结束即弃）。
  > **🔗 延伸** 与「上下文工程中长短期记忆如何实现」（已答）衔接；可聊记忆的遗忘/衰减策略与隐私合规。
- **Agent 单个节点的 Token 预算一般如何控制？为什么比想象中更重要？** —— 预算决定成本、延迟和注意力质量。出处：[[20-Areas/实习与求职/面试题与经验/AI-Agent开发岗位面经汇总-2026年4月-01至07|汇总B·面经07]]
  > [!success]- ✅ AI 解答 · Q73 · 2026-09-22
  > **🎯 标准答案（面试版）** 给每个节点设显式 Token 预算：输入侧=System+工具说明+检索内容+历史各有份额，输出侧=结构化结果+max_tokens 上限；超限走降级（摘要代原文、砍 few-shot、截断低优先级）。它比想象中重要，因为预算同时决定**成本**（循环中每轮重发上下文，O(n²) 累积）、**延迟**（生成长度）与**注意力质量**（超出有效窗口后中间信息召回骤降），超预算截断还会造成隐性失败。
  > **📌 要点**
  > - 先测量再优化：每节点记录 prompt/completion tokens
  > - 裁剪优先级：System > 当前任务 > 关键检索 > 近期历史 > 远期
  > - 工具大结果→字段抽取/摘要后再入上下文
  > - 输出用 JSON schema + max_tokens 双约束
  > **🔬 原理深入** 注意力是软资源：标称 128K 窗口≠有效 128K，"lost in the middle"（Liu et al., 2023）表明中间位置信息召回显著下降，所以预算的另一面是**信息排布**——关键内容放头尾。成本侧：Agent 循环每轮都携带全部历史重发，单节点多 2K tokens 经 30 轮循环放大为 60K+；工程上用 tiktoken 计数器+预算分配表，超限即触发压缩而非默默截断。
  > **🔗 延伸** 与「减少 Token 消耗」（Q74）、上下文压缩摘要题成套；面试可举一次实际省钱/提速的数据。
- **减少 Token 消耗体现在哪里？** —— Prompt 精简、历史裁剪、缓存、按需注入。出处：[[20-Areas/实习与求职/面试题与经验/AI-Agent与大模型岗位面经汇总-01至05-07-08|汇总A·面经04]]
  > [!success]- ✅ AI 解答 · Q74 · 2026-09-22
  > **🎯 标准答案（面试版）** 四个层面：① **Prompt 精简**——去冗余指令、模板复用；② **历史裁剪**——滑动窗口+摘要压缩，远期轮次不入上下文；③ **缓存**——Prompt Caching 复用稳定前缀（KV Cache 计费打折且降 TTFT），语义缓存复用相似问答；④ **按需注入**——工具说明、检索内容、few-shot 只在需要的节点给。再加模型分级：简单节点（分类/抽取）用小模型，复杂推理才用大模型。
  > **📌 要点**
  > - 前缀缓存：稳定内容前置，字节级一致才能命中
  > - 工具结果瘦身：字段过滤、截断+落库引用
  > - 动态按需：子 Agent 按需加载工具说明
  > - 监控大头：循环重发的历史与工具全文通常是成本主力
  > **🔬 原理深入** Prompt Caching 的机制是前缀 KV Cache 复用——只要前缀逐字节一致即可命中，因此 System、工具 schema、few-shot 这些稳定内容应前置，易变内容（当前时间、检索结果）后置。语义缓存则要警惕：embedding 相似≠答案等价，需相似度阈值+缓存失效与个性化隔离策略。优化顺序应基于按节点的 token 审计，先砍最大的浪费源。
  > **🔗 延伸** 与「Token 预算」（Q73）配套；可延伸成本评估体系（每会话/每任务成本核算）。

## 长短期记忆与压缩 🔥

- **上下文工程中长短期记忆如何实现？**（🔥）—— 短期靠窗口/State，长期靠向量库/文件化记忆。出处：[[20-Areas/实习与求职/面试题与经验/AI-Agent与大模型岗位面经汇总-01至05-07-08|汇总A·面经07]]
  > [!success]- ✅ AI 解答 · Q07 · 2026-09-15
  > **🎯 标准答案（面试版）**短期记忆 = 当前会话的上下文窗口与运行时 State：对话历史、scratchpad、任务清单，随任务结束即弃。长期记忆 = 跨会话持久化：语义知识存向量库按相似度检索；用户偏好/事实类信息用结构化 KV 或文件（mem0、Letta/MemGPT 的记忆块、Claude 的 memory tool）；重要事件写情景日志。关键在读写策略：写入要筛选（什么值得记），读取要排序（相关度+时间+重要性），并定期做遗忘与合并防止记忆库腐化。
  > **📌 要点**
  > - 短期 = 窗口/State；长期 = 向量库 + KV/文件 + 情景日志
  > - 写入策略：任务目标、用户偏好、纠错反馈三类优先
  > - 检索排序决定记忆质量，宁缺毋滥
  > **🔬 原理深入**
  > MemGPT 的核心思想是把操作系统的虚拟内存搬到 LLM：主上下文当 RAM、外部存储当磁盘，由模型自己发起换页（通过 memory 编辑工具调用）。实践中『写什么』比『存哪里』更难——无差别记录会让检索噪声污染上下文，反而降低表现。
  > **🔗 延伸**
  > 可对比记忆系统与 RAG 的边界（交互历史 vs 静态知识），以及隐私与 TTL 设计。
- **如何解决记忆覆盖问题？** —— 记忆版本化、冲突检测、合并策略。出处：[[20-Areas/实习与求职/面试题与经验/AI-Agent与大模型岗位面经汇总-01至05-07-08|汇总A·面经07]]
  > [!success]- ✅ AI 解答 · Q75 · 2026-09-22
  > **🎯 标准答案（面试版）** 记忆覆盖指新信息错误改写/抹除旧记忆。解法三层：① **版本化+追加写**——写入不覆盖旧值，append-only 日志保留历史、可回滚，定期 compaction 合并；② **冲突检测**——新记忆与旧记忆做相似度/实体对齐比对，发现「同一属性不同值」走合并策略（时间戳新者优先、置信度加权、或让模型仲裁）；③ **保护性记忆**——用户明确表达的事实/偏好打标记，不允许静默修改。
  > **📌 要点**
  > - append-only + compaction，事件溯源思想
  > - 冲突检测：embedding 相似度+实体对齐
  > - 合并策略：LWW 简单但危险，仲裁式更稳
  > - 记忆带元数据：来源/时间/置信度/访问频次
  > - 可解释：能回答「系统为什么认为我是这样的人」
  > **🔬 原理深入** 数据库界早有答案：MVCC 与事件溯源——不可变事件流+物化视图。LLM 场景的特有难点是**自然语言记忆没有 schema**：「用户喜欢 A」与「用户不再喜欢 A」的冲突无法靠键值覆盖判断，必须语义级比较（判断是更新、补充还是矛盾）。工程上还会给记忆加**置信度衰减**：久未验证的旧记忆随新证据降权，而非硬删除。
  > **🔗 延伸** mem0 的 ADD/UPDATE/DELETE/NOOP 记忆操作决策；与长期记忆（已答）、记忆压缩题成套。
- **记忆压缩如何实现，摘要如何生成？** —— 分层摘要、触发时机、增量摘要。出处：[[20-Areas/实习与求职/面试题与经验/AI-Agent开发岗位面经汇总-2026年4月-01至07|汇总B·面经04]]
  > [!success]- ✅ AI 解答 · Q76 · 2026-09-22
  > **🎯 标准答案（面试版）** 记忆压缩=把长历史折叠成紧凑表示。主流做法：① **分层摘要**——历史达到阈值（如窗口 70%）触发，旧轮次压成摘要，保留最近 N 轮原文（滚动窗口+摘要并存）；② **增量摘要**——新对话与旧摘要融合生成新摘要，成本 O(1) 而非全量重摘；③ **结构化抽取**——除散文摘要外，把实体/事实/决策抽成结构化条目入库，便于精准检索。
  > **📌 要点**
  > - 触发时机：token 阈值、轮数阈值、闲时异步触发
  > - 摘要要求：保住任务目标、关键决策、未决问题、用户偏好
  > - 增量融合：旧摘要+新增内容→新摘要，避免漂移与成本暴涨
  > - 原文指针：摘要附消息区间引用，可回溯验证
  > **🔬 原理深入** 增量而非全量的理由：全量重摘随历史增长成本线性上升，且每次「重新解读」可能引入语义漂移（摘要的摘要的摘要）。Claude Code 的 auto-compact 是典型工程实现：接近窗口上限自动压缩、保留近期原文。摘要必然有损——所以必须与「防扭曲」机制（原文指针、关键信息白名单）配套，摘要定位是**索引**而非真相源。
  > **🔗 延伸** Letta 分层摘要、compaction 机制；与「摘要防扭曲」（Q77）直接衔接。
- **提取摘要时如何避免摘要错误导致上下文扭曲？** —— 保留原文指针、摘要置信度、人工抽检。出处：[[20-Areas/实习与求职/面试题与经验/AI-Agent开发岗位面经汇总-2026年4月-01至07|汇总B·面经03]]
  > [!success]- ✅ AI 解答 · Q77 · 2026-09-22
  > **🎯 标准答案（面试版）** 核心思路：让摘要**可追溯、可校验、可回滚**。① 保留原文指针——每个摘要条目附消息区间引用，存疑可回查原文；② 关键信息不进摘要——硬约束、数字、日期、用户红线原样保留或单独结构化存储，不指望摘要保真；③ 生成后校验——用另一次调用对照原文逐条核对，低置信条目标记或丢弃；④ 抽检+回滚——评测抽样与人工抽检，发现扭曲回退上一版摘要。
  > **📌 要点**
  > - cite-or-keep：关键论断必须能对应原文位置
  > - 双轨制：事实进结构库、叙事进散文摘要
  > - 不可压缩清单：用户身份、任务目标、红线约束常驻
  > - 多份摘要一致性比对提升置信度
  > **🔬 原理深入** 危险在于**错误放大链**：摘要→被当作事实依据→再被压缩→错误逐层固化（context poisoning），且后续模型无从察觉。因此压缩必须保守：宁长勿错；摘要回答「大概聊过什么」，真相源始终是原始消息与结构化事实库。评测上构造带金标准的对话集，跑「压缩后问答准确率」回归，压缩策略改动必须过回归。
  > **🔗 延伸** 与记忆覆盖（Q75）、幻觉治理（已答）同属「上下文可靠性」专题。

## Prompt / Context / Harness 工程 🔥

- **Prompt 工程、Context 工程和 Harness 工程的区别是什么？**（🔥，概念边界必背）—— Prompt 是单次输入内容，Context 是模型可见全部信息的管理，Harness 是执行护栏与运行时。出处：[[20-Areas/实习与求职/面试题与经验/AI-Agent与大模型岗位面经汇总-01至05-07-08|汇总A·面经04]]，相关概念笔记 [[30-Resources/AI/Agent/长时运行 Agent 的有效 Harness]]
  > [!success]- ✅ AI 解答 · Q08 · 2026-09-15
  > **🎯 标准答案（面试版）**三者是逐层放大的关系。Prompt 工程关注单次调用里『怎么说』：指令措辞、few-shot、输出格式；Context 工程关注每次调用『模型能看到什么』：系统提示、工具定义与返回结果、检索内容、历史与状态的组装与取舍，本质是在有限窗口内做信息预算；Harness 工程关注模型外围的运行时：Agent 循环、工具执行、重试与降级、权限护栏、评估与监控。即 Prompt ⊂ Context ⊂ Harness。
  > **📌 要点**
  > - Prompt = 一次调用的输入文本
  > - Context = 模型可见的全部信息的管理
  > - Harness = 执行护栏与运行时，决定失败语义
  > **🔬 原理深入**
  > 只优化 Prompt 的收益有天花板，因为失败往往源于『模型没看到关键信息』（Context 问题）或『出错后没有纠错回路』（Harness 问题）。Context 工程把信息当稀缺资源做预算分配；Harness 决定长时运行 Agent 的可靠性上限——重试、熔断、审计都在这一层。
  > **🔗 延伸**
  > 可结合 Anthropic 关于 effective agents/harness 的工程文章，或本人项目中三层的实践例子。
- **System Prompt 如何设计？** —— 角色、约束、输出格式、工具说明的结构化组织。出处：[[20-Areas/实习与求职/面试题与经验/AI-Agent开发岗位面经汇总-2026年4月-01至07|汇总B·面经04]]
  > [!success]- ✅ AI 解答 · Q78 · 2026-09-22
  > **🎯 标准答案（面试版）** System Prompt 要结构化而非堆砌，经典分五节：① 身份与角色（你是谁、语气风格）；② 硬约束与红线（安全边界、禁做事项）——放最前面并用强指令+正反例；③ 工具说明（何时用/何时不用、参数含义、失败处理）；④ 输出格式（JSON schema 或 1-2 个范例）；⑤ 工作流程（步骤化指引）。原则：具体优于抽象、示例优于长篇描述、稳定内容前置以命中缓存。
  > **📌 要点**
  > - 红线用「必须/绝不」+反例示范
  > - 工具说明写清使用边界与失败兜底
  > - 输出格式给 schema，降低解析失败率
  > - 版本化+评测集回归，改一句跑一遍
  > - System 属稳定前缀：频繁改写会打碎 Prompt Cache
  > **🔬 原理深入** 注意力布局决定写法：开头与结尾注意力最高，超长 System 的中段最易被忽略——重要约束别埋中间。另一个反直觉点：**System 不是越长越好**，每条指令都在消耗模型的「遵循预算」，冗余与互相冲突的规则会稀释整体遵循率；上线前应做指令消融（删一条看效果变化）。
  > **🔗 延伸** Anthropic 官方 prompt engineering 指南；与 Prompt/Context/Harness 边界题（已答）对照。
- **Prompt 相关问题（面经05 泛问）。** —— 结合自己项目的 Prompt 编写经验准备。出处：[[20-Areas/实习与求职/面试题与经验/AI-Agent与大模型岗位面经汇总-01至05-07-08|汇总A·面经05]]
  > [!success]- ✅ AI 解答 · Q79 · 2026-09-22
  > **🎯 标准答案（面试版）** 这是开放性经验题，考的是有没有把 Prompt 当「代码」管理。答题主线：需求→初版（角色+任务+格式）→暴露问题（输出不稳/格式错/幻觉）→定位原因（描述含糊、缺示例、缺约束）→单变量修改→评测集回归→沉淀模板。准备 2~3 个有数据的真实案例最有说服力，例如「加 2 个 few-shot 后格式错误率 30%→5%」「引入结构化输出后解析失败清零」。
  > **📌 要点**
  > - 讲迭代过程：问题→假设→改动→验证，而非罗列技巧
  > - 方法论：变量隔离（一次只改一处）、评测集回归、版本管理
  > - 工具链：prompt 管理平台、A/B、LLM-as-judge 辅助评估
  > - 坦诚边界：Prompt 非万能，必要时配后处理或换模型
  > **🔬 原理深入** 面试官真正筛的是工程素养：Prompt 有没有版本号、评测集和 review 流程；模型升级后 Prompt 失效如何回归。常见追问要备好：「Prompt 对模型版本敏感怎么办」——答案仍是评测集+适配层；「多人协作怎么改 Prompt」——PR 流程+变更影响面说明。
  > **🔗 延伸** 与 Q80（Few-shot/意图识别）拼成一个完整故事；引用题库「AI Coding 与工程素养」类目思路。
- **Prompt 如何编写（要求展开说明）？意图识别如何理解？Few-shot 具体如何使用？** —— 结合项目：写 Prompt 的实际迭代过程、Few-shot 选样策略。出处：[[20-Areas/实习与求职/面试题与经验/AI-Agent开发岗位面经汇总-2026年4月-01至07|汇总B·面经06]]
  > [!success]- ✅ AI 解答 · Q80 · 2026-09-22
  > **🎯 标准答案（面试版）** 三小问一体回答。**Prompt 编写**：五要素结构 role/context/task/format/constraints，先明确任务定义再补示例，最后评测迭代。**意图识别**：把用户输入映射到预定义意图集合，通常小模型或嵌入分类实现，输出意图+置信度，低置信走澄清或兜底；它是路由和成本分层的前提。**Few-shot**：选与当前输入相似且有代表性的示例（覆盖典型+边界 case），示例格式与输出要求严格一致，2~5 个为宜。
  > **📌 要点**
  > - 意图识别两条路：判别式分类 vs 生成式结构化输出
  > - 意图+槽位两级：先粗分类再抽参数；低置信兜底
  > - Few-shot 动态化：embedding 检索最相似示例注入
  > - 示例里放一个「拒答/澄清」示范，教模型说「不知道」
  > **🔬 原理深入** Few-shot 的本质是 in-context learning：示例激活模型的模式补全能力，且存在**顺序偏差**与**多数标签偏差**（示例分布会拉偏输出），所以选样要均衡、与查询相关。动态 few-shot（检索式选例）通常优于固定示例。意图识别的容错设计：分类置信度阈值+澄清话术+兜底 Agent，避免错误路由放大成整条链路失败。
  > **🔗 延伸** 与 System Prompt 设计（Q78）、Agent 路由题呼应；可引 in-context learning 与 RAG 式示例检索。
- **除了 Prompt，还可以如何解决 AI Coding 代码冗长、复杂的问题？** —— 架构分层、检索增强、生成后约束校验。出处：[[20-Areas/实习与求职/面试题与经验/AI-Agent与大模型岗位面经汇总-01至05-07-08|汇总A·面经02]]
  > [!success]- ✅ AI 解答 · Q81 · 2026-09-23
  > **🎯 标准答案（面试版）**：代码冗长的根因不是提示词不够好，而是生成单元过大、缺少项目全局上下文。解法在工程侧：架构上分层解耦，把单次生成切成小而清晰的任务；用检索增强注入项目既有规范、相似实现与工具函数，避免重复造轮子；再在生成后加约束校验（静态检查、编译、单测、diff 审查），把「看起来对」升级为「可执行的正确」。
  > **📌 要点**
  > - 架构分层：模块化/接口化，控制单次生成单元的规模与边界
  > - 检索增强：注入代码规范、相似实现、API 文档，优先复用既有轮子
  > - 生成后约束：Lint/Sonar、编译与单测门禁、人工 diff 审查闭环
  > - 反馈迭代：把编译/测试报错回喂模型修复，形成 agentic loop
  > **🔬 原理深入**：模型是概率采样，缺少项目全局一致性与成本意识，一次性生成整个模块时倾向防御性堆料、重复实现已有工具函数。分层把任务切小后，上下文更聚焦、输出更克制；RAG 提供事实锚点抑制即兴发挥；约束校验把质量判断从人肉转移到自动化门禁，LLM-as-Judge 与 CI 规则可以把这套闭环跑成流水线。三者关系：分层控制「生成什么」，检索控制「依据什么生成」，校验控制「生成结果是否合格」。
  > **🔗 延伸**：追问：代码复杂度怎么量化？（圈复杂度、重复率、SonarQube 门禁）AI 生成代码的评审策略？（小步 PR + 人在回路 + 自动化摘要）

## 幻觉与可靠性

- **幻觉问题如何解决？**（🔥）—— RAG 注入事实、引用溯源、温度与输出约束、事后校验。出处：[[20-Areas/实习与求职/面试题与经验/AI-Agent与大模型岗位面经汇总-01至05-07-08|汇总A·面经05]]、[[20-Areas/实习与求职/面试题与经验/AI-Agent开发岗位面经汇总-2026年4月-01至07|汇总B·面经05]]
  > [!success]- ✅ AI 解答 · Q09 · 2026-09-15
  > **🎯 标准答案（面试版）**工程上以『接地+校验』为主线：①RAG 注入可核实的事实，并要求每个论断给出引用；②把『回答不知道』设计为合法输出（cite-or-abstain）；③事实型任务降低温度、用结构化输出约束格式；④增加事后校验：另一个模型/规则引擎审查，或用工具验证（计算器、代码执行）；⑤高风险场景用一致性采样（SelfCheckGPT 思路）检测可疑输出。模型侧靠事实性微调与 RLHF 缓解。
  > **📌 要点**
  > - RAG + 引用溯源是第一道防线
  > - 弃答合法化比强行回答更工程化
  > - 生成与验证分离，论断绑定证据
  > - 目标不是零幻觉，而是幻觉可被发现
  > **🔬 原理深入**
  > 幻觉的根源是模型按最大似然『补全』文本而非查证事实——训练目标是说得像而非说得对，因此无法根除，只能做系统级防御。实践中检索质量对事实性的影响常大于模型尺寸；Agent 场景里工具返回值是天然接地源。
  > **🔗 延伸**
  > 可聊评估指标（faithfulness、answer relevance）、LLM-as-judge 做自动化事实核查的局限。
- **AI 的局限性和不可靠性，遇到问题如何解决？** —— 兜底策略、人工介入、评测驱动。出处：[[20-Areas/实习与求职/面试题与经验/AI-Agent与大模型岗位面经汇总-01至05-07-08|汇总A·面经05]]
  > [!success]- ✅ AI 解答 · Q82 · 2026-09-23
  > **🎯 标准答案（面试版）**：承认 LLM 存在幻觉与输出不确定，无法根除只能工程化管理。做法是三层兜底：关键路径保留人工介入（human-in-the-loop），高危操作强制确认；用评测集持续驱动质量（eval-driven），badcase 回流防劣化；对不可靠输出做冗余设计——多次采样投票、双模型交叉校验、低置信度自动降级到规则或人工。
  > **📌 要点**
  > - 兜底策略：超时/异常/低置信度 → 降级规则引擎或转人工
  > - 人工介入：删库、支付等高危动作强制 human-in-the-loop，最小权限控爆炸半径
  > - 评测驱动：golden set 回归 + 幻觉率/准确率指标，发版前后对比防劣化
  > - 冗余校验：self-consistency 多数投票、verifier 模型复核、引用溯源
  > - 可观测：全链路 trace + 日志留存，问题可定位可回放
  > **🔬 原理深入**：LLM 的不可靠性来自概率采样与训练数据覆盖缺口，属于模型本性而非工程缺陷，因此「解决」的准确定义是让不可靠性可度量、可拦截。离线侧把幻觉率变成数字：构建真实 badcase 评测集，每次改 prompt/换模型都跑回归；在线侧用 self-consistency（同一问题多次采样取多数一致答案）与 verifier 二次审查提升精度。权限上遵循最小化原则——只给模型完成任务必需的工具与数据，即使幻觉触发了危险调用，影响面也被限制住。
  > **🔗 延伸**：常见追问：评测集怎么建？（线上 badcase 持续沉淀 + 定期人工扩充）线上如何发现幻觉？（强制引用溯源 + 用户反馈闭环打标）

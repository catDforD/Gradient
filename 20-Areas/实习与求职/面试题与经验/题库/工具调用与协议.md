# 工具调用与协议（Function Calling · MCP · Skills）

按知识类别整理的面试题库之二。题目从各面经抽取去重，🔥 表示在多份面经中重复出现（优先复习）。出处缩写见 [[20-Areas/实习与求职/面试题与经验/面试题与经验索引|索引]]。

## Function Calling 与 Tool 调用链

- **如何提升 Agent 的 Function Calling 能力？** —— 数据侧（工具调用样本微调）、Prompt 侧（工具描述质量）、工程侧（Schema 约束与校验）。出处：[[20-Areas/实习与求职/面试题与经验/AI-Agent与大模型岗位面经汇总-01至05-07-08|汇总A·面经07]]
  > [!success]- ✅ AI 解答 · Q108 · 2026-09-25
  > **🎯 标准答案（面试版）**三个层面：数据侧——用真实调用轨迹（含失败重试与参数修正样本）做 SFT，让模型学到工具选择与参数生成的先验；Prompt 侧——把工具描述写清「何时用/何时不用、参数含义+示例」，控制注入数量（工具多时检索式选择），命名稳定；工程侧——JSON Schema 严格约束+受约束解码保证参数合法，参数校验后把报错回喂给模型自我修正，外层加重试与兜底。
  > **📌 要点**
  > - 数据侧：高质量轨迹 SFT；「错误→修正」成对样本价值最高；RL 用任务完成率做奖励
  > - Prompt 侧：description 质量>数量；工具分组/RAG over tools 按需注入
  > - 工程侧：constrained decoding 从解码层杜绝非法 JSON；pydantic 校验+报错回传
  > - 评估：分层归因——选错工具/参数错/执行错，分别对应不同修法
  > - 闭环：线上失败案例→修复→评审集回归，防修一个坏一个
  > **🔬 原理深入**
  > Function Calling 失败三类根因：不知道工具存在（召回）、知道但选错（判别）、选对但参数错（生成）。对症：召回→检索式注入；判别→优化描述与 few-shot；生成→按 Schema 做 grammar-based sampling，在解码层面保证合法。报错回喂有效是因为执行环境充当了反馈源，模型可基于错误消息自我修正——这也是 ReAct 式纠错的原理。
  > **🔗 延伸**
  > 追问：工具太多怎么分层（先选组再选工具）；并行调用的参数冲突；微调 vs 工具检索的成本对比；描述改动的 A/B 怎么做。
- **Tool 什么时候发送给 LLM，什么时候真正执行？** —— 工具 Schema 随请求下发，模型输出 tool_call 后由运行时执行。出处：[[20-Areas/实习与求职/面试题与经验/AI-Agent开发岗位面经汇总-2026年4月-01至07|汇总B·面经04]]
  > [!success]- ✅ AI 解答 · Q109 · 2026-09-25
  > **🎯 标准答案（面试版）**发送与执行是两个独立阶段：发送的是工具 Schema（名称/描述/参数定义），随 LLM 请求下发（或按需检索注入），让模型「知道有什么工具」；模型不执行任何东西，只输出结构化 tool_call 意图（函数名+JSON 参数）；真正执行由运行时完成——校验参数、鉴权后调用真实实现（本地函数/RPC/MCP），再把结果回填上下文触发下一轮推理。
  > **📌 要点**
  > - 发送：请求体 tools 字段带 Schema；大工具集按需注入省 token
  > - 决策：模型只产出 tool_calls，无任何实际副作用
  > - 执行：解析→参数校验→权限检查→调用实现→异常捕获→结果序列化
  > - 循环：结果回填后模型继续，可连续多轮直至最终答复
  > - 安全：模型只能「提议」，执行权与白名单在运行时，高危操作加人工闸门
  > **🔬 原理深入**
  > 「意图与执行分离」是 Agent 安全的基石：LLM 是概率组件，直接给执行权等于把系统暴露给幻觉与提示注入。运行时是确定性守门员——Schema 校验挡格式错误、鉴权挡越权、白名单挡未注册调用。成本上 Schema 每轮重发占 token（大工具集可达数万 token），优化手段是工具检索注入与 prompt caching。
  > **🔗 延伸**
  > 追问：并行工具调用（无依赖时并发执行）；执行结果过大怎么办（截断/摘要/落盘引用）；哪些操作需要人工确认。
- **返回结果后，系统如何判断需要调用哪个 Tool？** —— 解析 tool_call、参数校验、路由分发。出处：[[20-Areas/实习与求职/面试题与经验/AI-Agent开发岗位面经汇总-2026年4月-01至07|汇总B·面经04]]
  > [!success]- ✅ AI 解答 · Q110 · 2026-09-25
  > **🎯 标准答案（面试版）**区分两个「判断」：选哪个工具是模型的事——工具结果回填上下文后，模型基于新上下文输出下一个动作（继续 tool_call 或给最终回答）；系统只做「路由与分发」：解析 tool_call（名称+参数），在注册表查对应实现，做参数校验与鉴权后执行。系统不「猜」工具，只忠实执行模型决策并保证执行正确。
  > **📌 要点**
  > - 解析：从响应提取 tool_calls（name、arguments、call_id）
  > - 校验：Schema 校验（类型/必填/枚举）+业务校验（范围/权限）
  > - 路由：注册表 name→handler；未注册工具返回明确错误让模型自我修正
  > - 回填：结果封装为 role=tool 消息，按 tool_call_id 与请求精确配对
  > - 终止：模型无 tool_call 即结束；另有步数/Token 预算熔断兜底
  > **🔬 原理深入**
  > 这是「模型当大脑、运行时当小脑」的循环：工具选择需要语义理解所以放模型侧，系统侧只做确定性保障。工程关键点是并行工具调用时结果必须按 call_id 精确回填，错位会让上下文混乱、模型开始胡乱调用。终止要有双保险：模型自然终止+系统最大步数熔断，防无限循环。调试多轮链路要对每轮的 tool_call 与结果做 trace。
  > **🔗 延伸**
  > 追问：模型坚持调用不存在/无权限工具怎么办（错误回喂+重试上限）；回填顺序错乱的处理；如何做工具链路的可观测。
- **`@Tool` 注解方式的底层如何实现？** —— 反射 + Schema 生成 + 注册机制（Spring AI / LangChain4j 风格）。出处：[[20-Areas/实习与求职/面试题与经验/AI-Agent开发岗位面经汇总-2026年4月-01至07|汇总B·面经03]]
  > [!success]- ✅ AI 解答 · Q111 · 2026-09-26
  > **🎯 标准答案（面试版）**注解方式本质是「声明式工具注册」：框架启动时扫描带 @Tool 的方法，通过反射读取方法签名、参数注解与文档注释，自动生成 JSON Schema 形式的工具定义并注册进工具表；运行期模型下发 tool_call，框架按名称查表，反射（配合 Jackson 绑参）调用真实方法，返回值序列化后回填给模型。开发者只写业务方法，Schema 生成、参数校验、调用分发全部由框架完成。
  > **📌 要点**
  > - 启动期：类路径扫描 → 反射读方法/参数/注解 → 生成 name+description+inputSchema
  > - 注册期：包装成统一 ToolCallback 入表，随请求注入模型 tools 字段
  > - 运行期：tool_call 按名路由 → Jackson 绑参 → Method.invoke → 结果序列化回填
  > - 描述来源是注解属性与参数文档，其质量直接决定模型调用准确率
  > - 校验在框架层统一做：参数 schema 校验、异常包装、超时控制
  > **🔬 原理深入**
  > 为什么用反射而不是编译期代码生成？反射零侵入、与依赖注入/热插拔天然兼容，代价是启动开销与反射性能（可用 MethodHandle 与元数据缓存缓解）。最容易出错的环节是 JSON Schema 与 Java 类型的映射：泛型擦除会让 schema 不精确、重载方法产生歧义，所以框架普遍建议工具方法避免重载、参数用明确 POJO、字段语义写全。
  > **🔗 延伸**
  > LangChain4j 的 @Tool、Spring AI 的 @Tool/@McpTool 都是同一思路；把同一套注解方法同时暴露为 MCP server 工具，是当前很常见的架构。

## Function Calling / MCP / Skills 概念边界 🔥

- **Function Calling、MCP、Skills 有什么区别？**（🔥，高频必背）—— FC 是模型能力，MCP 是标准化工具接入协议，Skills 是可复用的知识/流程包。出处：[[20-Areas/实习与求职/面试题与经验/AI-Agent开发岗位面经汇总-2026年4月-01至07|汇总B·面经03]]、[[20-Areas/实习与求职/面试题与经验/AI-Agent与大模型岗位面经汇总-01至05-07-08|汇总A·面经04]]
  > [!success]- ✅ AI 解答 · Q11 · 2026-09-16
  > **🎯 标准答案（面试版）**三者是不同层面的概念：Function Calling 是模型能力——LLM 根据工具 Schema 输出结构化调用请求；MCP 是协议层标准——统一模型应用与外部工具/数据源的接入方式，解决生态集成的 N×M 问题；Skills 是应用层的知识/流程封装——把领域知识、操作 SOP 打包成可按需注入的技能包。一句话串联：FC 是「会说工具调用」，MCP 是「统一插头标准」，Skills 是「按需加载的操作手册」。
  > **📌 要点**
  > - FC：模型输出 tool_call（JSON），运行时执行后回填结果继续生成；能力由训练与工具描述质量共同决定
  > - MCP：Client-Host-Server 架构，tools/resources/prompts 三类原语，支持 stdio/HTTP 传输，一次接入处处复用
  > - Skills：SKILL.md 指令 + 脚本/资源的文件化封装，按任务相关性动态注入，不占常驻上下文
  > - 关系：MCP Server 的工具最终仍靠 FC 被模型调用；Skills 常用于指导模型如何组合使用工具
  > **🔬 原理深入**
  > 三个概念各自解决不同矛盾：FC 解决「模型如何发起调用」（结构化输出训练 + Schema 约束解码）；MCP 解决「工具生态集成」——工具方实现一次 Server 即可被所有支持 MCP 的客户端使用（类比 USB-C）；Skills 解决「上下文经济性」——常驻系统提示放不下所有领域 know-how，按需加载 + 渐进披露。常见追问：MCP 会替代 FC 吗？不会，MCP 是工具分发协议，调用执行仍走 FC；Skills 与 RAG 的区别？RAG 召回事实用于回答，Skills 加载流程用于改变行为。
  > **🔗 延伸**
  > 可结合自己项目展开：工具用 MCP 统一接入、领域 SOP 沉淀为 Skill、模型侧用工具调用样本微调提升 FC 准确率；再引到文件内「MCP 工程化」小节的传输适配与版本兼容题。

  > [!success]- ✅ AI 解答 · Q11 · 2026-10-01（复习轮）
  > **🎯 标准答案（面试版）**一句话定位+趋势判断：FC 是模型能力（按 Schema 输出结构化调用），MCP 是协议标准（工具接入的「USB-C」），Skills 是知识封装（按需加载的操作手册）。2026 年答法补一句趋势：MCP 已成 Agent 工具接入的事实标准、Skills 生态快速爆发、FC 被各家 SDK 抽象为默认能力——三者正走向「MCP 供能力、Skill 供流程、FC 负责执行」的标准分层。
  > **📌 要点**
  > - 答题节奏：先分层定位，再各举一个自己项目的实例，最后讲协同关系
  > - 反例澄清必说：「MCP 会替代 FC 吗」——不会，MCP 分发工具，调用仍靠 FC
  > - Skill vs RAG 一句话：RAG 召回事实改「知道什么」，Skill 加载流程改「怎么做」
  > **🔬 原理深入** 为什么需要三个抽象？分别解决三个不同矛盾：FC 解决「模型如何发起调用」（结构化输出+约束解码）、MCP 解决「生态集成的 N×M 问题」（实现一次处处复用）、Skills 解决「上下文经济性」（常驻放不下就按需加载）。能把三个矛盾讲清，抽象就不是背概念而是推导结果。
  > **🔗 延伸** 与 Q112（Skills 趋势）、Q113（MCP vs Skill）串联成组合拳；每个抽象各备一个量化收益（接入人日、token 成本、任务通过率）应对追问。
- **为什么 Skills 会逐渐成为流行趋势？** —— 按需注入控制上下文长度、跨场景复用、可观测、更新不改代码。出处：[[20-Areas/实习与求职/面试题与经验/AI-Agent开发岗位面经汇总-2026年4月-01至07|汇总B·面经03]]
  > [!success]- ✅ AI 解答 · Q112 · 2026-09-26
  > **🎯 标准答案（面试版）**Skills 把「完成某类任务的知识与流程」打包成可版本化的文件包（说明文档+可选脚本+资源），Agent 按需加载。流行的三个原因：一是上下文经济性——操作手册不必全塞进系统提示，用到才注入，显著控制 token 成本；二是知识与代码解耦——更新技能不改代码不重启，走 git 评审即可；三是可复用可分享——同一技能能跨项目、跨会话甚至跨平台迁移，逐渐形成生态。
  > **📌 要点**
  > - 按需加载（渐进式披露）：元数据常驻上下文，正文用到才读
  > - 知识资产化：markdown 可读可评审可版本化，迭代成本远低于改代码
  > - 组合性：技能内部可调用工具/MCP/脚本，把流程封装成原子能力
  > - 长任务友好：稳定的操作规程让多步任务产出一致
  > **🔬 原理深入**
  > 与三种传统方案对比更能说明趋势必然性：全写进 Prompt 会上下文膨胀且难维护；微调成本高、迭代以周计；写死工具只解决「能力」不解决「流程知识」。Skill 的定位是程序性知识的载体——把 prompt 工程的成果文件化、可管理化。它与 Agent 长任务化的时间点吻合：任务越长，越需要稳定可复用的规程而非一次性提示。
  > **🔗 延伸**
  > Anthropic Agent Skills、AstrBot Skills 等在推同一抽象；与 MCP 的关系是知识层与协议层互补（详见下题）。
- **MCP 和 Skill 的区别是什么？** —— 协议层 vs 知识层。出处：[[20-Areas/实习与求职/面试题与经验/AI-Agent与大模型岗位面经汇总-01至05-07-08|汇总A·面经04]]
  > [!success]- ✅ AI 解答 · Q113 · 2026-09-26
  > **🎯 标准答案（面试版）**MCP 是协议层：标准化的客户端-服务端协议（JSON-RPC，stdio/HTTP 等传输），负责让 Agent 以统一方式发现并调用外部工具、资源与提示，解决「能力接入」。Skill 是知识层：以 markdown 为主的说明文件（可附脚本），告诉模型某类任务该怎么做，解决「流程知识」。一个管手脚、一个管方法论，互补而非替代。
  > **📌 要点**
  > - MCP：跨进程/跨机器，需要运行 server，有连接与能力协商生命周期
  > - Skill：纯文件，注入上下文即生效，无协议开销，随用随加载
  > - 组合形态：Skill 在步骤里指导模型调用 MCP 工具完成真实动作
  > - 失效模式不同：MCP 挂在网络/协议/服务可用性；Skill 败在描述不清或上下文污染
  > **🔬 原理深入**
  > 选型判据：能力需要真实副作用（调 API、查库、写文件）就走 MCP；只需把「怎么做事」讲给模型（规范、checklist、最佳实践）就用 Skill。两个反模式：全做成 MCP 工具会让工具列表膨胀且丢失流程上下文；全写成 Skill 又执行不了真实动作。面试时用「手脚 vs 方法论」的比喻最容易讲清。
  > **🔗 延伸**
  > 实践中最佳组合是「Skill 编排流程 + MCP 提供原子能力」，二者共用同一套权限与审计体系。
- **在华为项目里 MCP 和 Skill 主要如何使用？** —— 结合自己项目准备实例。出处：[[20-Areas/实习与求职/面试题与经验/AI-Agent与大模型岗位面经汇总-01至05-07-08|汇总A·面经04]]
  > [!success]- ✅ AI 解答 · Q114 · 2026-09-26
  > **🎯 标准答案（面试版）**这题考项目结合，答题框架是「MCP 管能力接入，Skill 管流程沉淀」+ 具体实例。MCP 侧示例：把代码库检索、CI/CD 平台、内部文档系统分别封装成 MCP server，统一协议接入 Agent 平台——新增工具不必改 Agent 代码，权限与审计集中收口。Skill 侧示例：把「发版检查单」「线上故障排查手册」「需求拆解规范」写成技能文件，执行对应任务时按需加载，保证不同人触发同一流程时步骤一致。
  > **📌 要点**
  > - 选 MCP 的理由：跨团队复用、与 Agent 运行时解耦、权限审计收口
  > - 选 Skill 的理由：流程知识迭代频繁、需要评审与版本化、降低提示词维护冲突
  > - 落地效果：新工具接入从「改代码排期」变「注册即用」，操作一致性提升
  > - 用数字佐证：接入一个新工具的人日变化、任务一次通过率变化
  > **🔬 原理深入**
  > 面试官想听的其实是权衡：为什么不直接 function calling？——每换一个 Agent 运行时都要重写一遍工具绑定，跨团队无法复用。为什么不把流程全写系统提示？——上下文膨胀，多人维护 prompt 必然冲突。把协议层/知识层的抽象讲清楚，再给一两个量化效果即可；若没做过华为项目，用自己项目里的同类结构替换，框架不变。
  > **🔗 延伸**
  > 可延伸到与内部权限体系、审计日志的集成方式，体现工程完整度。

## Skills 知识进化（小红书重点）🔥

## MCP 工程化

- **如何适配 stdio、HTTP、SSE、Streamable HTTP？** —— 各传输方式的连接生命周期、适用场景与适配层设计。出处：[[20-Areas/实习与求职/面试题与经验/小红书-Agent服务端开发实习-一面面经|小红书·服务端]]
  > [!success]- ✅ AI 解答 · Q117 · 2026-09-26
  > **🎯 标准答案（面试版）**四种是 MCP 传输层的不同形态。stdio：本地子进程，JSON-RPC 走 stdin/stdout，生命周期随进程拉起/退出，适合本地工具（IDE 插件、CLI）。HTTP+SSE（旧远程方案）：GET /sse 建立下行事件流获取消息端点，POST 上行发送，双端点有状态。Streamable HTTP（2025-03 规范引入，取代前者）：单一端点 POST，响应可选升级为 SSE 流，用 Mcp-Session-Id 维持会话。适配层设计：统一 connect/send/reconnect 抽象，每种 transport 各自实现连接生命周期管理（进程管理、会话保活、断线重连、幂等重试）。
  > **📌 要点**
  > - stdio：零网络开销、本地信任，进程退出即会话结束
  > - HTTP+SSE：双端点、有状态、对网关与负载均衡不友好——已被取代
  > - Streamable HTTP：单端点 + 可选流式 + 会话头，基础设施兼容性最好
  > - 适配层：统一接口 + 多实现 + 健康检查与重连策略
  > **🔬 原理深入**
  > 选型逻辑：本地能力用 stdio（简单可靠），远程/多租户用 Streamable HTTP（可过网关、可水平扩展）。HTTP+SSE 双端点的痛点是必须有状态会话且两条路由，网关配置复杂；Streamable HTTP 把下行流做成可选响应，普通请求-响应也能跑，这是它能取代 SSE 的根本原因。断线处理上，Streamable HTTP 可通过 Last-Event-ID 续传事件。
  > **🔗 延伸**
  > 客户端按 server 声明协商传输方式；对老 server 保留 HTTP+SSE 兼容模式是常见过渡方案。
- **如何处理 MCP 版本兼容问题？** —— 能力协商、协议变更记录、兼容层与降级策略。出处：[[20-Areas/实习与求职/面试题与经验/小红书-Agent服务端开发实习-一面面经|小红书·服务端]]
  > [!success]- ✅ AI 解答 · Q118 · 2026-09-26
  > **🎯 标准答案（面试版）**三板斧：能力协商——initialize 握手交换 protocolVersion 与 capabilities，双方按声明交集运行，不支持的功能优雅降级；兼容层——客户端同时实现多版本传输与消息格式（如 HTTP+SSE 与 Streamable HTTP 双支持），服务端声明支持范围并保持增量演进（新增字段可选化，不破坏旧客户端）；治理——记录协议变更（spec 2024-11-05 → 2025-03-26 → 2025-06-18），升级前跑 client×server 兼容性测试矩阵，工具列表变化用 tools/list_changed 通知客户端刷新。
  > **📌 要点**
  > - 协商：版本取交集 + capability 开关，不支持即降级
  > - 演进原则：只增不删、字段可选、语义不变
  > - 运行保障：测试矩阵、灰度发布、回滚预案
  > - 观测：版本上报 + 不兼容报错监控
  > **🔬 原理深入**
  > 协议兼容的本质是契约管理：MCP 用 JSON-RPC 加显式版本协商，比隐式 REST 演进更可控。难点在破坏性变更——例如 Streamable HTTP 取代 HTTP+SSE，规范做法是新旧并存一个过渡期，客户端按 server 协商结果降级，而不是硬切。工程上还要注意 server 端工具 schema 的演进：新增参数必须可选，否则旧 prompt 硬编码调用会直接失败。
  > **🔗 延伸**
  > 可对比 gRPC 的 API 版本管理（包路径版本号、弃用周期），思路相通。
- **将 Choice 接口封装成 MCP 工具时，为什么参数设计和输出约束都很关键？** —— 参数清晰度影响模型调用准确率，输出约束影响下游解析。出处：[[20-Areas/实习与求职/面试题与经验/AI-Agent开发岗位面经汇总-2026年4月-01至07|汇总B·面经07]]

  > **🎯 标准答案（面试版）**模型选择工具和填参数的唯一依据是 name/description/inputSchema——参数设计含糊会直接推高调用错误率（选错工具、幻觉参数、必填漏填）；输出约束决定结果能否被程序与模型稳定消费——无结构自由文本会污染上下文、让下游解析失败、也无法做错误归因。所以封装时参数要「少而准、枚举化、带示例」，输出要「结构化、可截断、错误可读」。
  > **📌 要点**
  > - 参数：语义命名、一工具一职责、必填/可选分明、枚举约束、描述含单位与示例
  > - 避免深嵌套大对象与重载歧义；复杂查询拆成多个简单工具

  > 本质是从「人机接口设计」换成「模型接口设计」：模型不看 UI 不看代码，schema 与 description 就是全部——接口即提示词。经验上 description 里写一句「何时不该用本工具」能显著降低误调用率；输出中附「下一步建议」（缺失参数、可续接的工具）能提升多轮任务成功率。这两类设计都应纳入工具上线前的调用成功率评估。
  > **🔗 延伸**
  > 可补充：用真实调用轨迹（含失败样本）做回归集，量化每次 schema 改动的收益。
- **MCP 工具接入后，模型调用工具前后的处理流程通常是什么？** —— 请求前注入工具描述 → 模型决策 → 执行 → 结果回填 → 模型继续。出处：[[20-Areas/实习与求职/面试题与经验/AI-Agent开发岗位面经汇总-2026年4月-01至07|汇总B·面经07]]

  > **🎯 标准答案（面试版）**完整链路：初始化时 client 与 server 握手并拉取 tools/list（name/description/inputSchema），把工具定义随请求注入模型 tools 字段；用户请求进来后，模型基于上下文决策输出 tool_use（工具名 + JSON 参数）；客户端校验参数（schema、权限）后通过 tools/call 发给 server 执行；执行结果作为 tool result 消息回填上下文，模型继续推理——若还需要信息就再次发起调用，循环直到产出最终答复。
  > **📌 要点**
  > - 前置：工具发现（list）与描述注入；工具多时做检索式选择
  > - 调用：模型输出结构化 tool_use → 客户端校验 → server 执行
  > - 回填：结果与错误都进上下文，错误可触发模型自纠
  > - 循环控制：最大轮数、并行调用、高危操作人工确认
  > **🔬 原理深入**
  > 两个常被追问的点：一是上下文管理——大结果要截断或摘要，否则几轮就撑爆窗口；二是职责边界——模型只负责「决定调什么、传什么参数」，执行与鉴权在客户端/服务端完成，这是安全的分界线（人工审批、审计日志都在这一层做）。另外注意多工具并行调用时结果的对应关系要靠 tool_call_id 对齐。
  > **🔗 延伸**
  > 这个循环就是 ReAct 模式的工程化形态；对照 LangChain 的 AgentExecutor 或 OpenAI tool use 流程理解更顺。

## 流式输出与通信协议 🔥

- **SSE 和 WebSocket 的区别？** —— 单向 vs 双向、HTTP 兼容性、断线重连。出处：[[20-Areas/实习与求职/面试题与经验/AI-Agent开发岗位面经汇总-2026年4月-01至07|汇总B·面经05]]
  > [!success]- ✅ AI 解答 · Q121 · 2026-09-27
  > **🎯 标准答案（面试版）**SSE（Server-Sent Events）是基于 HTTP 的单向服务器推送协议（Content-Type: text/event-stream），只能服务端向客户端推流，但天然复用 HTTP 的鉴权、代理、CDN、负载均衡等基建，并内置断线自动重连（浏览器 EventSource 自动携带 Last-Event-ID 请求续传）。WebSocket 是独立协议，通过 HTTP 101 Upgrade 握手升级为 ws:// 长连接，提供全双工双向通道、支持二进制帧，但连接管理和基础设施（网关、心跳、粘性会话）都要额外建设。选型上，LLM 流式输出这种「一次请求、单向流式响应」场景首选 SSE；只有协作编辑、即时通信等真正需要双向实时才用 WebSocket。
  > **📌 要点**
  > - 方向：SSE 单向（服务端→客户端），WebSocket 全双工
  > - 载体：SSE 跑在普通 HTTP 上，WebSocket 独立协议（101 升级握手）
  > - 重连：SSE 原生 auto-reconnect + Last-Event-ID 续传，WebSocket 需自实现
  > - 基建：SSE 兼容现有 HTTP 网关/CDN；WebSocket 需专门支持（心跳、sticky）
  > - 格式：SSE 文本帧（event/data/id/retry 字段），WebSocket 支持二进制
  > **🔬 原理深入**
  > 细节上：SSE 报文以字段行组成、空行分隔事件，服务端用注释行「: ping」做心跳防代理空闲断连；HTTP/1.1 下浏览器对同域名 SSE 有 6 连接限制（HTTP/2 多路复用解决）。WebSocket 握手用 Sec-WebSocket-Key/Accept 校验，鉴权只在握手时完成，后续帧没有 header，因此长连接内的权限变更、token 过期要额外设计。追问「LLM 流式为什么不用 WebSocket」：响应单向、复用 HTTP 重试与鉴权语义、客户端实现简单，WebSocket 的双向能力是纯开销。反向追问「WebSocket 优势场景」：服务端要主动、高频、双向推（协同光标、联机对战）。
  > **🔗 延伸**
  > OpenAI/Anthropic 流式接口均采用 SSE；MCP 的 Streamable HTTP 传输也是 POST+SSE 组合；gRPC server-streaming 是同场景的另一选择。
- **为什么使用 SSE 而不使用 flux？（原帖疑为 fetch 流式，待核实）** —— 流式选型理由：协议简单、HTTP 基建兼容、代理友好。出处：[[20-Areas/实习与求职/面试题与经验/AI-Agent开发岗位面经汇总-2026年4月-01至07|汇总B·面经02]]
  > [!success]- ✅ AI 解答 · Q122 · 2026-09-27
  > **🎯 标准答案（面试版）**先澄清：原帖「flux」疑为 fetch 拼写误差，按 fetch 流式（ReadableStream）理解。两者并非互斥：SSE 是服务端的线格式（wire format）约定，fetch 是客户端接收手段，生产上常见「服务端按 SSE 格式输出 + 客户端用 fetch+ReadableStream 解析」的混合方案。选 SSE 的理由：它是标准协议，事件语义完整（event/data/id/retry），浏览器 EventSource 原生支持并自动重连；纯 fetch 方案里分帧、半包拼接、断线重连都要手写。而反过来 EventSource 也有硬伤：只支持 GET、不能带请求体和自定义 Header，所以需要 POST 长 prompt 的对话场景只能用 fetch 接流。
  > **📌 要点**
  > - SSE=线格式，fetch=接收 API，维度不同可组合
  > - EventSource 原生自动重连；fetch 方案重连/分帧自己实现
  > - EventSource 只能 GET、无法带 body/自定义 Header → 对话场景必须 fetch
  > - 生产混合方案：SSE 格式输出 + fetch ReadableStream 解析
  > **🔬 原理深入**
  > 实现 fetch 流式解析的要点：reader.read() 循环读取 Uint8Array，需维护缓冲区处理跨 chunk 的半包（一条 event 可能被从中间截断），按空行切事件、去掉「data: 」前缀、遇到 [DONE] 哨兵结束，用 AbortController 支持用户中断。面试主动说明「flux 应为 fetch，我按 fetch 流式理解」能体现严谨；再补一句「若面试官指 react-flux 则与本问题无关」可展示沟通确认意识。
  > **🔗 延伸**
  > 对比各家：OpenAI SDK 的 stream=True 底层同样是 SSE 解析；Vercel AI SDK 抽象掉了 SSE/fetch 差异，是前端接入的省事选择。
- **流式输出使用的是哪种协议？** 出处：[[20-Areas/实习与求职/面试题与经验/AI-Agent开发岗位面经汇总-2026年4月-01至07|汇总B·面经03]]
  > [!success]- ✅ AI 解答 · Q123 · 2026-09-27
  > **🎯 标准答案（面试版）**业界事实标准是 SSE（text/event-stream）：调用 OpenAI 兼容接口时请求体带 stream:true，响应即 SSE 流；自研后端（FastAPI/Express）向前端推 token 也普遍用 SSE。token 天然是「单向、有序、增量」的小消息，与 SSE 的语义完美匹配；只有强双向需求才考虑 WebSocket。客户端用 EventSource 或 fetch 流式解析均可。
  > **📌 要点**
  > - 请求带 stream:true，响应 Content-Type: text/event-stream
  > - data: 帧承载增量，[DONE] 哨兵表示结束
  > - 底层是 HTTP chunked transfer，SSE 在其上定义事件语义
  > - 反向代理必须关闭缓冲，否则表现为「卡住后一次性吐出」
  > **🔬 原理深入**
  > 最高频追问是「为什么流式卡住半天一次性出来」：Nginx 等反向代理默认开启响应缓冲（proxy_buffering on），会攒满 buffer 才转发，需要 proxy_buffering off 或响应头 X-Accel-Buffering: no；同理 gzip 压缩也会引入缓冲，流式接口常关闭压缩或改用无缓冲压缩。另外 HTTP 分块传输保证「按序到达」但 不保证「实时到达」，任何一层缓冲都会破坏实时性——排查顺序：应用层生成器是否阻塞 → uvicorn worker → 代理缓冲 → 客户端渲染节流。
  > **🔗 延伸**
  > Anthropic API 同为 SSE；GraphQL Subscriptions（常走 WebSocket）与 gRPC streaming 是替代方案，各有基础设施成本。
- **调用 OpenAI API 后，后台协议是怎样的一套工作流？** —— 请求体 → Chat Completions → SSE 分块（delta）→ 拼装。出处：[[20-Areas/实习与求职/面试题与经验/AI-Agent开发岗位面经汇总-2026年4月-01至07|汇总B·面经01]]
  > [!success]- ✅ AI 解答 · Q124 · 2026-09-27
  > **🎯 标准答案（面试版）**完整链路：客户端组装 messages、tools、stream:true 后 POST /v1/chat/completions → 服务端鉴权、拼接上下文、模型逐 token 生成 → 以 SSE 帧下发增量：首帧 delta 带 role，随后 content 或 tool_calls 碎片（带 index，arguments 是 JSON 字符串分片），最终帧给 finish_reason，再发 data: [DONE] 结束 → 客户端边收边按 index 聚合拼装。若 finish_reason=tool_calls，客户端执行工具并把结果以 role:tool 消息追加进 messages 发起下一轮请求，循环直到 finish_reason=stop 得到最终回答。
  > **📌 要点**
  > - delta 结构：role → content 增量 → tool_calls 碎片（index+arguments 分片）
  > - finish_reason：stop / tool_calls / length，驱动客户端下一步动作
  > - [DONE] 哨兵结束流；usage 需 stream_options.include_usage 才返回
  > - 工具调用是「执行→回填→再请求」的多轮循环，不是一次完成
  > **🔬 原理深入**
  > 客户端解析的工程细节：跨帧半包要缓冲拼接；tool_calls 的 arguments 按 index 聚合成完整 JSON 后才能 parse 并执行；停止原因 length 表示截断，要做续写。异常路径：SSE 中断无法续传（连接断了只能整轮重发，注意消息幂等与已执行工具的副作用），超时与空响应要有兜底。服务端一侧：推理引擎（vLLM 等）产出 token → 框架封装 delta 帧 → chunked 下发，网关层同样要注意缓冲问题。
  > **🔗 延伸**
  > Responses API 与 MCP 把工具循环进一步标准化；function 参数的 JSON Schema 校验失败时服务端/客户端的重试策略是常见追问点。
- **FastAPI + SSE 做流式输出时，后端如何把多节点执行结果实时推送给前端？** —— 生成器/事件队列按节点产出推送。出处：[[20-Areas/实习与求职/面试题与经验/AI-Agent开发岗位面经汇总-2026年4月-01至07|汇总B·面经07]]
  > [!success]- ✅ AI 解答 · Q125 · 2026-09-27
  > **🎯 标准答案（面试版）**核心模式是「异步生成器 + 事件队列」：为每个 SSE 连接建一个 asyncio.Queue，Agent 图每个节点（规划、检索、工具调用、生成等）执行完就把自己产出的中间结果/状态增量 put 进队列；接口返回 StreamingResponse(async_generator(), media_type='text/event-stream')，生成器内循环 await queue.get()，把事件包装成 data: {json}

 下发；全部节点完成时推送结束事件并退出循环关闭连接。节点执行与推送跑在同一事件循环里，天然并发、按产出即时推送。
  > **📌 要点**
  > - StreamingResponse + async generator 是骨架，media_type 必须 text/event-stream
  > - asyncio.Queue 做节点→连接的事件通道，事件带 node/step/type/payload
  > - 结束哨兵事件 + 连接关闭；客户端断开要清理（request.is_disconnected/GeneratorExit）
  > - 响应头：Cache-Control: no-cache、X-Accel-Buffering: no（防代理缓冲）
  > **🔬 原理深入**
  > 工程细节：①节点内长任务用 asyncio.create_task 异步执行，结果路由回 queue，异常也要包装成 error 事件推送而不是静默吞掉；②同步阻塞函数会卡死整个事件循环，必须 run_in_executor 或改异步客户端；③多 worker/多机部署时，执行节点与 SSE 连接可能不在同一进程，需 Redis Pub/Sub 等跨进程转发事件，或会话粘滞路由；④推送心跳注释帧（: keep-alive）防止网关空闲超时断连；⑤事件里带序号便于前端乱序兜底与调试。追问「为什么不用 WebSocket」同前述选型逻辑。
  > **🔗 延伸**
  > LangGraph 的 astream_events 原生产出节点级事件流，桥接 SSE 只需格式转换；前端 React 用 fetch 流 + 状态机渲染各节点进度即可。

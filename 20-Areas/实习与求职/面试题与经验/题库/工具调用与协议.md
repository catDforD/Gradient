# 工具调用与协议（Function Calling · MCP · Skills）

按知识类别整理的面试题库之二。题目从各面经抽取去重，🔥 表示在多份面经中重复出现（优先复习）。出处缩写见 [[20-Areas/实习与求职/面试题与经验/面试题与经验索引|索引]]。

## Function Calling 与 Tool 调用链

- **如何提升 Agent 的 Function Calling 能力？** —— 数据侧（工具调用样本微调）、Prompt 侧（工具描述质量）、工程侧（Schema 约束与校验）。出处：[[20-Areas/实习与求职/面试题与经验/AI-Agent与大模型岗位面经汇总-01至05-07-08|汇总A·面经07]]
  > [!success]- ✅ AI 解答 · Q108 · 2026-09-25
  > **🎯 标准答案（面试版）**三个层面：数据侧——用真实调用轨迹（含失败重试与参数修正样本）做 SFT，让模型学到工具选择与参数生成的先验；Prompt 侧——把工具描述写清「何时用/何时不用、参数含义+示例」，控制注入数量（工具多时检索式选择），命名稳定；工程侧——JSON Schema 严格约束+受约束解码保证参数合法，参数校验后把报错回喂给模型自我修正，外层加重试与兜底。
  > **📌 要点**
  > - 数据侧：高质量轨迹 SFT；「错误→修正」成对样本价值最高；RL 用任务完成率做奖励
  > - Prompt 侧：description 质量>数量；工具分组/RAG over tools 按需注入
  > - 工程侧：constrained decoding 从解码层杜绝非法 JSON；pydantic 校验+报错回传
  > - 评估：分层归因——选错工具/参数错/执行错，分别对应不同修法
  > - 闭环：线上失败案例→修复→评审集回归，防修一个坏一个
  > **🔬 原理深入**
  > Function Calling 失败三类根因：不知道工具存在（召回）、知道但选错（判别）、选对但参数错（生成）。对症：召回→检索式注入；判别→优化描述与 few-shot；生成→按 Schema 做 grammar-based sampling，在解码层面保证合法。报错回喂有效是因为执行环境充当了反馈源，模型可基于错误消息自我修正——这也是 ReAct 式纠错的原理。
  > **🔗 延伸**
  > 追问：工具太多怎么分层（先选组再选工具）；并行调用的参数冲突；微调 vs 工具检索的成本对比；描述改动的 A/B 怎么做。
- **Tool 什么时候发送给 LLM，什么时候真正执行？** —— 工具 Schema 随请求下发，模型输出 tool_call 后由运行时执行。出处：[[20-Areas/实习与求职/面试题与经验/AI-Agent开发岗位面经汇总-2026年4月-01至07|汇总B·面经04]]
  > [!success]- ✅ AI 解答 · Q109 · 2026-09-25
  > **🎯 标准答案（面试版）**发送与执行是两个独立阶段：发送的是工具 Schema（名称/描述/参数定义），随 LLM 请求下发（或按需检索注入），让模型「知道有什么工具」；模型不执行任何东西，只输出结构化 tool_call 意图（函数名+JSON 参数）；真正执行由运行时完成——校验参数、鉴权后调用真实实现（本地函数/RPC/MCP），再把结果回填上下文触发下一轮推理。
  > **📌 要点**
  > - 发送：请求体 tools 字段带 Schema；大工具集按需注入省 token
  > - 决策：模型只产出 tool_calls，无任何实际副作用
  > - 执行：解析→参数校验→权限检查→调用实现→异常捕获→结果序列化
  > - 循环：结果回填后模型继续，可连续多轮直至最终答复
  > - 安全：模型只能「提议」，执行权与白名单在运行时，高危操作加人工闸门
  > **🔬 原理深入**
  > 「意图与执行分离」是 Agent 安全的基石：LLM 是概率组件，直接给执行权等于把系统暴露给幻觉与提示注入。运行时是确定性守门员——Schema 校验挡格式错误、鉴权挡越权、白名单挡未注册调用。成本上 Schema 每轮重发占 token（大工具集可达数万 token），优化手段是工具检索注入与 prompt caching。
  > **🔗 延伸**
  > 追问：并行工具调用（无依赖时并发执行）；执行结果过大怎么办（截断/摘要/落盘引用）；哪些操作需要人工确认。
- **返回结果后，系统如何判断需要调用哪个 Tool？** —— 解析 tool_call、参数校验、路由分发。出处：[[20-Areas/实习与求职/面试题与经验/AI-Agent开发岗位面经汇总-2026年4月-01至07|汇总B·面经04]]
  > [!success]- ✅ AI 解答 · Q110 · 2026-09-25
  > **🎯 标准答案（面试版）**区分两个「判断」：选哪个工具是模型的事——工具结果回填上下文后，模型基于新上下文输出下一个动作（继续 tool_call 或给最终回答）；系统只做「路由与分发」：解析 tool_call（名称+参数），在注册表查对应实现，做参数校验与鉴权后执行。系统不「猜」工具，只忠实执行模型决策并保证执行正确。
  > **📌 要点**
  > - 解析：从响应提取 tool_calls（name、arguments、call_id）
  > - 校验：Schema 校验（类型/必填/枚举）+业务校验（范围/权限）
  > - 路由：注册表 name→handler；未注册工具返回明确错误让模型自我修正
  > - 回填：结果封装为 role=tool 消息，按 tool_call_id 与请求精确配对
  > - 终止：模型无 tool_call 即结束；另有步数/Token 预算熔断兜底
  > **🔬 原理深入**
  > 这是「模型当大脑、运行时当小脑」的循环：工具选择需要语义理解所以放模型侧，系统侧只做确定性保障。工程关键点是并行工具调用时结果必须按 call_id 精确回填，错位会让上下文混乱、模型开始胡乱调用。终止要有双保险：模型自然终止+系统最大步数熔断，防无限循环。调试多轮链路要对每轮的 tool_call 与结果做 trace。
  > **🔗 延伸**
  > 追问：模型坚持调用不存在/无权限工具怎么办（错误回喂+重试上限）；回填顺序错乱的处理；如何做工具链路的可观测。
- **`@Tool` 注解方式的底层如何实现？** —— 反射 + Schema 生成 + 注册机制（Spring AI / LangChain4j 风格）。出处：[[20-Areas/实习与求职/面试题与经验/AI-Agent开发岗位面经汇总-2026年4月-01至07|汇总B·面经03]]

## Function Calling / MCP / Skills 概念边界 🔥

- **Function Calling、MCP、Skills 有什么区别？**（🔥，高频必背）—— FC 是模型能力，MCP 是标准化工具接入协议，Skills 是可复用的知识/流程包。出处：[[20-Areas/实习与求职/面试题与经验/AI-Agent开发岗位面经汇总-2026年4月-01至07|汇总B·面经03]]、[[20-Areas/实习与求职/面试题与经验/AI-Agent与大模型岗位面经汇总-01至05-07-08|汇总A·面经04]]
  > [!success]- ✅ AI 解答 · Q11 · 2026-09-16
  > **🎯 标准答案（面试版）**三者是不同层面的概念：Function Calling 是模型能力——LLM 根据工具 Schema 输出结构化调用请求；MCP 是协议层标准——统一模型应用与外部工具/数据源的接入方式，解决生态集成的 N×M 问题；Skills 是应用层的知识/流程封装——把领域知识、操作 SOP 打包成可按需注入的技能包。一句话串联：FC 是「会说工具调用」，MCP 是「统一插头标准」，Skills 是「按需加载的操作手册」。
  > **📌 要点**
  > - FC：模型输出 tool_call（JSON），运行时执行后回填结果继续生成；能力由训练与工具描述质量共同决定
  > - MCP：Client-Host-Server 架构，tools/resources/prompts 三类原语，支持 stdio/HTTP 传输，一次接入处处复用
  > - Skills：SKILL.md 指令 + 脚本/资源的文件化封装，按任务相关性动态注入，不占常驻上下文
  > - 关系：MCP Server 的工具最终仍靠 FC 被模型调用；Skills 常用于指导模型如何组合使用工具
  > **🔬 原理深入**
  > 三个概念各自解决不同矛盾：FC 解决「模型如何发起调用」（结构化输出训练 + Schema 约束解码）；MCP 解决「工具生态集成」——工具方实现一次 Server 即可被所有支持 MCP 的客户端使用（类比 USB-C）；Skills 解决「上下文经济性」——常驻系统提示放不下所有领域 know-how，按需加载 + 渐进披露。常见追问：MCP 会替代 FC 吗？不会，MCP 是工具分发协议，调用执行仍走 FC；Skills 与 RAG 的区别？RAG 召回事实用于回答，Skills 加载流程用于改变行为。
  > **🔗 延伸**
  > 可结合自己项目展开：工具用 MCP 统一接入、领域 SOP 沉淀为 Skill、模型侧用工具调用样本微调提升 FC 准确率；再引到文件内「MCP 工程化」小节的传输适配与版本兼容题。
- **为什么 Skills 会逐渐成为流行趋势？** —— 按需注入控制上下文长度、跨场景复用、可观测、更新不改代码。出处：[[20-Areas/实习与求职/面试题与经验/AI-Agent开发岗位面经汇总-2026年4月-01至07|汇总B·面经03]]
- **MCP 和 Skill 的区别是什么？** —— 协议层 vs 知识层。出处：[[20-Areas/实习与求职/面试题与经验/AI-Agent与大模型岗位面经汇总-01至05-07-08|汇总A·面经04]]
- **在华为项目里 MCP 和 Skill 主要如何使用？** —— 结合自己项目准备实例。出处：[[20-Areas/实习与求职/面试题与经验/AI-Agent与大模型岗位面经汇总-01至05-07-08|汇总A·面经04]]

## Skills 知识进化（小红书重点）🔥

- **怎么搭建 Skills 知识进化的流程？**（🔥）—— 收集→提取→存储→检查→应用→反馈闭环。出处：[[20-Areas/实习与求职/面试题与经验/小红书-Agent开发实习生-一面面经-AIGC小白入门记|小红书·AIGC小白入门记]]、[[20-Areas/实习与求职/面试题与经验/小红书Agent开发实习生一面-百度Agent面经-杰尼龟|小红书/百度·杰尼龟]]
  > [!success]- ✅ AI 解答 · Q12 · 2026-09-16
  > **🎯 标准答案（面试版）**核心是一条用例驱动的闭环：收集（从对话日志、失败案例、人工经验中收集原始知识）→ 提取（去噪并结构化为带触发条件的 SKILL.md）→ 存储（版本化仓库）→ 检查（用历史用例回归验证有效性，质量门禁）→ 应用（按任务相关性检索并注入会话）→ 反馈（按使用效果评分，修订或淘汰，触发新一轮提取）。
  > **📌 要点**
  > - 收集双通道：人工沉淀 + Agent 运行日志挖掘（成功轨迹提炼经验、失败教训反推规则）
  > - 结构化字段：名称、描述（何时触发）、指令正文、可选脚本/模板
  > - 质量门禁：入库前回归验证，宁缺毋滥，防过时/错误知识污染
  > - 应用与反馈：注入后记录是否被使用、效果如何，差的降权修订，形成数据飞轮
  > **🔬 原理深入**
  > 本质是把上下文工程「数据化、版本化」，相当于给知识建 CI/CD。系统要平衡三对矛盾：新鲜度 vs 稳定性（灰度上线、A/B 验证）、个性化 vs 共享（个人记忆库与团队 Skill 库分层）、自动化 vs 可控（AI 提稿 + 人工审核合入）。常见追问：如何自动发现「该生成新 Skill 的时刻」？——对失败轨迹做聚类、挖掘高频人工纠正模式，命中即触发知识提取流程。
  > **🔗 延伸**
  > 与记忆系统的边界：记忆偏个人化、情景化，Skills 偏规范化、可复用；成熟实践中可从个人记忆中「结晶」出团队级 Skill。可引到下一题「为什么用 Skills 而非 Prompt」。
- **为什么不直接把知识写进 Prompt，而使用 Skills 方式？**（🔥）—— Prompt 长度、知识更新成本、多场景复用、可观测性、维护成本五维对比。出处：[[20-Areas/实习与求职/面试题与经验/小红书-Agent开发实习生-一面面经-AIGC小白入门记|小红书·AIGC小白入门记]]、[[20-Areas/实习与求职/面试题与经验/小红书Agent开发实习生一面-百度Agent面经-杰尼龟|小红书/百度·杰尼龟]]
  > [!success]- ✅ AI 解答 · Q13 · 2026-09-16
  > **🎯 标准答案（面试版）**五维对比：①上下文长度——知识全塞 Prompt 挤占有效上下文且稀释关键信息，Skills 按需注入；②更新成本——改 Prompt 要改代码发版，Skills 是数据，改文件即生效、可版本化回滚；③多场景复用——Skill 跨项目跨 Agent 复用，Prompt 与单一场景绑定；④可观测性——注入了哪个 Skill、是否被采纳可追踪评估，Prompt 知识是黑盒；⑤维护成本——Skill 可分工维护、有质量门禁，巨型 Prompt 无人敢动。
  > **📌 要点**
  > - Token 经济学：常驻 Prompt 每次请求都付费，Skills 仅相关任务加载
  > - 注意力稀释：上下文越长中部信息召回越低（lost in the middle）
  > - 关注点分离：稳定全局行为放系统提示，易变领域知识放 Skill
  > - 安全与审计：Skill 分库管理、可独立审计与回滚
  > **🔬 原理深入**
  > 这是「配置 vs 代码」之争在 LLM 时代的重演：把知识当数据（data-driven）才能建立迭代飞轮。从注意力机制看，上下文越长单条信息获得的平均注意力越低，「大而全 Prompt」不仅贵还降准确率；Skills 的按需注入等价于上下文的「虚拟内存」——工作集动态换入换出。追问：什么时候就该写进 Prompt？——高频、稳定、全局的行为规范（输出格式、安全边界）适合系统提示；低频、领域化、易变的知识适合 Skill。
  > **🔗 延伸**
  > 可对比 RAG（检索事实用于回答）与 Skills（加载流程改变行为）、微调（能力内化）三者的适用层级，展示知识管理的完整视图。

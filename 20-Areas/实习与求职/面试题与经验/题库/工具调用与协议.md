  > **🎯 标准答案（面试版）**先归因再修：Function Calling 失败分三类——不知道工具存在（**召回**）、知道但选错（**判别**）、选对但参数错（**生成**）。对应三修法：召回问题→工具检索式注入+分组分层；判别问题→优化 description（写清何时用/何时不用+示例）+few-shot；生成问题→JSON Schema 约束 + grammar-based 受约束解码 + 参数校验后把报错回喂自我修正。数据侧用「错误→修正」成对轨迹做 SFT，工程侧加重试与兜底。
  > **📌 要点**
  > - description 质量 > 数量：工具集大时按需检索注入，命名与语义保持稳定避免模型混乱
  > - 受约束解码从解码层杜绝非法 JSON，比事后校验+重试更省轮次
  > - 「错误→修正」成对样本是最有价值的微调数据；RL 可用任务完成率做奖励信号
  > - 评估要分层归因（选错工具/参数错/执行错），否则修一个坏一个
  > - 闭环：线上失败案例→归因→修复→评审集回归
  > **🔬 原理深入** 报错回喂之所以有效，是因为执行环境充当了「确定性反馈源」——模型可基于真实错误信息自我修正，这正是 ReAct 式纠错的机理。微调 vs 工具检索是成本取舍：微调能内化调用先验但更新慢、样本贵；检索注入灵活但吃 token，且大工具集下本身会引发召回噪声。实践顺序：先 prompt/schema 工程（成本最低），不够再上数据侧，最后才考虑微调。
  > **🔗 延伸** 追问：工具太多怎么分层（先选组再选工具）；并行调用的参数冲突与依赖判断；描述改动的 A/B 如何设计；MCP 生态下工具来源异构（自建+第三方）如何统一质量与鉴权。

  > - 闭环：线上失败案例→修复→评审集回归，防修一个坏一个

  > **🎯 标准答案（面试版）**注解方式本质是「声明式工具注册」：框架启动时扫描带 @Tool 的方法，通过反射读取方法签名、参数注解与文档注释，自动生成 JSON Schema 形式的工具定义并注册进工具表；运行期模型下发 tool_call，框架按名称查表，反射（配合 Jackson 绑参）调用真实方法，返回值序列化后回填给模型。开发者只写业务方法，Schema 生成、参数校验、调用分发全部由框架完成。
  > **📌 要点**
  > - 启动期：类路径扫描 → 反射读方法/参数/注解 → 生成 name+description+inputSchema
  > - 注册期：包装成统一 ToolCallback 入表，随请求注入模型 tools 字段
  > - 运行期：tool_call 按名路由 → Jackson 绑参 → Method.invoke → 结果序列化回填
  > - 描述来源是注解属性与参数文档，其质量直接决定模型调用准确率
  > - 校验在框架层统一做：参数 schema 校验、异常包装、超时控制

  > LangChain4j 的 @Tool、Spring AI 的 @Tool/@McpTool 都是同一思路；把同一套注解方法同时暴露为 MCP server 工具，是当前很常见的架构。

## Function Calling / MCP / Skills 概念边界 🔥

- **Function Calling、MCP、Skills 有什么区别？**（🔥，高频必背）—— FC 是模型能力，MCP 是标准化工具接入协议，Skills 是可复用的知识/流程包。出处：[[20-Areas/实习与求职/面试题与经验/AI-Agent开发岗位面经汇总-2026年4月-01至07|汇总B·面经03]]、[[20-Areas/实习与求职/面试题与经验/AI-Agent与大模型岗位面经汇总-01至05-07-08|汇总A·面经04]]
  > [!success]- ✅ AI 解答 · Q11 · 2026-09-16
  > **🎯 标准答案（面试版）**三者是不同层面的概念：Function Calling 是模型能力——LLM 根据工具 Schema 输出结构化调用请求；MCP 是协议层标准——统一模型应用与外部工具/数据源的接入方式，解决生态集成的 N×M 问题；Skills 是应用层的知识/流程封装——把领域知识、操作 SOP 打包成可按需注入的技能包。一句话串联：FC 是「会说工具调用」，MCP 是「统一插头标准」，Skills 是「按需加载的操作手册」。
  > **📌 要点**
  > - FC：模型输出 tool_call（JSON），运行时执行后回填结果继续生成；能力由训练与工具描述质量共同决定
  > - MCP：Client-Host-Server 架构，tools/resources/prompts 三类原语，支持 stdio/HTTP 传输，一次接入处处复用
  > - Skills：SKILL.md 指令 + 脚本/资源的文件化封装，按任务相关性动态注入，不占常驻上下文

- **如何适配 stdio、HTTP、SSE、Streamable HTTP？** —— 各传输方式的连接生命周期、适用场景与适配层设计。出处：[[20-Areas/实习与求职/面试题与经验/小红书-Agent服务端开发实习-一面面经|小红书·服务端]]
  > [!success]- ✅ AI 解答 · Q117 · 2026-09-26
  > **🎯 标准答案（面试版）**四种是 MCP 传输层的不同形态。stdio：本地子进程，JSON-RPC 走 stdin/stdout，生命周期随进程拉起/退出，适合本地工具（IDE 插件、CLI）。HTTP+SSE（旧远程方案）：GET /sse 建立下行事件流获取消息端点，POST 上行发送，双端点有状态。Streamable HTTP（2025-03 规范引入，取代前者）：单一端点 POST，响应可选升级为 SSE 流，用 Mcp-Session-Id 维持会话。适配层设计：统一 connect/send/reconnect 抽象，每种 transport 各自实现连接生命周期管理（进程管理、会话保活、断线重连、幂等重试）。
  > **📌 要点**
  > - stdio：零网络开销、本地信任，进程退出即会话结束
  > - HTTP+SSE：双端点、有状态、对网关与负载均衡不友好——已被取代
  > - Streamable HTTP：单端点 + 可选流式 + 会话头，基础设施兼容性最好
  > - 适配层：统一接口 + 多实现 + 健康检查与重连策略
  > **🔬 原理深入**
  > 选型逻辑：本地能力用 stdio（简单可靠），远程/多租户用 Streamable HTTP（可过网关、可水平扩展）。HTTP+SSE 双端点的痛点是必须有状态会话且两条路由，网关配置复杂；Streamable HTTP 把下行流做成可选响应，普通请求-响应也能跑，这是它能取代 SSE 的根本原因。断线处理上，Streamable HTTP 可通过 Last-Event-ID 续传事件。
  > **🔗 延伸**
  > 客户端按 server 声明协商传输方式；对老 server 保留 HTTP+SSE 兼容模式是常见过渡方案。

  > [!success]- ✅ AI 解答 · Q117 · 2026-10-13（复习轮）

  > **📌 要点**
  > - 抽象接口 + 多实现 + 健康检查与自动重连，是适配层的骨架
  > - stdio：零网络开销、本地信任，进程退出即会话结束
  > - HTTP+SSE：双端点在网关/负载均衡下配置复杂、需粘性会话——已被取代

- **SSE 和 WebSocket 的区别？** —— 单向 vs 双向、HTTP 兼容性、断线重连。出处：[[20-Areas/实习与求职/面试题与经验/AI-Agent开发岗位面经汇总-2026年4月-01至07|汇总B·面经05]]
  > [!success]- ✅ AI 解答 · Q121 · 2026-09-27
  > **🎯 标准答案（面试版）**SSE（Server-Sent Events）是基于 HTTP 的单向服务器推送协议（Content-Type: text/event-stream），只能服务端向客户端推流，但天然复用 HTTP 的鉴权、代理、CDN、负载均衡等基建，并内置断线自动重连（浏览器 EventSource 自动携带 Last-Event-ID 请求续传）。WebSocket 是独立协议，通过 HTTP 101 Upgrade 握手升级为 ws:// 长连接，提供全双工双向通道、支持二进制帧，但连接管理和基础设施（网关、心跳、粘性会话）都要额外建设。选型上，LLM 流式输出这种「一次请求、单向流式响应」场景首选 SSE；只有协作编辑、即时通信等真正需要双向实时才用 WebSocket。
  > **📌 要点**
  > - 方向：SSE 单向（服务端→客户端），WebSocket 全双工
  > - 载体：SSE 跑在普通 HTTP 上，WebSocket 独立协议（101 升级握手）
  > - 重连：SSE 原生 auto-reconnect + Last-Event-ID 续传，WebSocket 需自实现
  > - 基建：SSE 兼容现有 HTTP 网关/CDN；WebSocket 需专门支持（心跳、sticky）
  > - 格式：SSE 文本帧（event/data/id/retry 字段），WebSocket 支持二进制
  > **🔬 原理深入**
  > 细节上：SSE 报文以字段行组成、空行分隔事件，服务端用注释行「: ping」做心跳防代理空闲断连；HTTP/1.1 下浏览器对同域名 SSE 有 6 连接限制（HTTP/2 多路复用解决）。WebSocket 握手用 Sec-WebSocket-Key/Accept 校验，鉴权只在握手时完成，后续帧没有 header，因此长连接内的权限变更、token 过期要额外设计。追问「LLM 流式为什么不用 WebSocket」：响应单向、复用 HTTP 重试与鉴权语义、客户端实现简单，WebSocket 的双向能力是纯开销。反向追问「WebSocket 优势场景」：服务端要主动、高频、双向推（协同光标、联机对战）。
  > **🔗 延伸**
  > OpenAI/Anthropic 流式接口均采用 SSE；MCP 的 Streamable HTTP 传输也是 POST+SSE 组合；gRPC server-streaming 是同场景的另一选择。

  > 背压问题：若渲染慢而 token 快，数据会在缓冲区堆积，可读 reader 的 flow 适配（暂停读取）或丢弃中间态只留最新。EventSource 只支持 GET 的绕行方案有三：polyfill 库（fetch-event-source）、把参数塞 URL（有长度与泄露风险）、或改用 POST+fetch（推荐）。

  > 可对比 Vercel AI SDK／openai-node 的 stream helper：它们把 SSE 解析与增量渲染都封装了，面试里说「生产直接用成熟库、但要讲清它内部做了什么」最能体现工程成熟度。
- **流式输出使用的是哪种协议？** 出处：[[20-Areas/实习与求职/面试题与经验/AI-Agent开发岗位面经汇总-2026年4月-01至07|汇总B·面经03]]
  > [!success]- ✅ AI 解答 · Q123 · 2026-09-27
  > **🎯 标准答案（面试版）**业界事实标准是 SSE（text/event-stream）：调用 OpenAI 兼容接口时请求体带 stream:true，响应即 SSE 流；自研后端（FastAPI/Express）向前端推 token 也普遍用 SSE。token 天然是「单向、有序、增量」的小消息，与 SSE 的语义完美匹配；只有强双向需求才考虑 WebSocket。客户端用 EventSource 或 fetch 流式解析均可。
  > **📌 要点**
  > - 请求带 stream:true，响应 Content-Type: text/event-stream
  > - data: 帧承载增量，[DONE] 哨兵表示结束
  > - 底层是 HTTP chunked transfer，SSE 在其上定义事件语义
  > - 反向代理必须关闭缓冲，否则表现为「卡住后一次性吐出」
  > **🔬 原理深入**
  > 最高频追问是「为什么流式卡住半天一次性出来」：Nginx 等反向代理默认开启响应缓冲（proxy_buffering on），会攒满 buffer 才转发，需要 proxy_buffering off 或响应头 X-Accel-Buffering: no；同理 gzip 压缩也会引入缓冲，流式接口常关闭压缩或改用无缓冲压缩。另外 HTTP 分块传输保证「按序到达」但 不保证「实时到达」，任何一层缓冲都会破坏实时性——排查顺序：应用层生成器是否阻塞 → uvicorn worker → 代理缓冲 → 客户端渲染节流。
  > **🔗 延伸**
  > Anthropic API 同为 SSE；GraphQL Subscriptions（常走 WebSocket）与 gRPC streaming 是替代方案，各有基础设施成本。

  > [!success]- ✅ AI 解答 · Q123 · 2026-10-14（复习轮）
  > **🎯 标准答案（面试版）**一句话：事实标准是 SSE（text/event-stream），底层 HTTP chunked。要能报出「一段链路 + 一组参数」：客户端(EventSource/fetch) → 网关/反代(Nginx/ALB/Cloudflare) → 应用(FastAPI/uvicorn) → 模型推理(vLLM)。每一跳都有超时与缓冲开关，任何一处没配对都会表现为「先卡住、再一次性吐出」。
  > **📌 要点**
  > - Nginx：proxy_buffering off + X-Accel-Buffering: no，proxy_read_timeout 调大
  > - Cloudflare 免费版有约 100s 响应限制；ALB idle timeout 默认 60s，需调大
  > - uvicorn：--timeout-keep-alive 与 workers 数影响长连接稳定性
  > - 排查顺序：应用生成器是否阻塞 → worker 是否死锁 → 反代缓冲 → 客户端渲染节流
  > **🔬 原理深入**
  > 排查手段可报命令级细节：`curl -N -H 'Accept: text/event-stream' <url>` 分段验证每一跳，用 time 看首字节时间（TTFB）；若能拿到网关日志，对比「后端首字节时间」与「客户端首字节时间」即可定位缓冲层。监控指标建议：TTFT（首 token 延迟）、token/s、连接存活时长、异常断连率——这四项是流式体验的核心 SLO。
  > **🔗 延伸**
  > 可引申到「流式的可观测性」：把一次会话的 trace 串起来（请求 id → 各节点耗时 → 首 token 时间），面试官通常会对这种端到端视角加分。

  > - delta 结构：role → content 增量 → tool_calls 碎片（index+arguments 分片）
  > - finish_reason：stop / tool_calls / length，驱动客户端下一步动作

  > Responses API 与 MCP 把工具循环进一步标准化；function 参数的 JSON Schema 校验失败时服务端/客户端的重试策略是常见追问点。

  > **🎯 标准答案（面试版）**核心模式是「异步生成器 + 事件队列」：为每个 SSE 连接建一个 asyncio.Queue，Agent 图每个节点（规划、检索、工具调用、生成等）执行完就把自己产出的中间结果/状态增量 put 进队列；接口返回 StreamingResponse(async_generator(), media_type='text/event-stream')，生成器内循环 await queue.get()，把事件包装成 data: {json}

  > [!success]- ✅ AI 解答 · Q125 · 2026-10-14（复习轮）
  > **🎯 标准答案（面试版）**原模式的三个生产化补丁：①多 worker 下 asyncio.Queue 不跨进程，需用 Redis Pub/Sub 或 Stream 做广播，让任意 worker 都能把事件送给持有连接的进程；②断线要能续传，事件带自增 id 并做环形缓冲（或落库），重连时按 Last-Event-ID 回放；③队列必须有界 + 背压策略（满了丢中间态、保最终态），否则慢客户端会把内存拖爆。
  > **📌 要点**
  > - 事件协议设计：event 类型化（node_start/node_delta/tool_call/error/final）+ 自增 id
  > - 单进程内 asyncio.Queue 够用；多进程/K8s 多副本必须外部广播（Redis/NATS）
  > - 有界队列 + 丢弃策略 + 客户端可主动「拉全量」兜底
  > - 并发保护：每连接占一个协程，用 semaphore 限制同时在跑的 Agent 数
  > **🔬 原理深入**
  > 追问「为什么不用 WebSocket 做多副本广播」：问题不在传输层而在「连接落在哪个副本」，广播通道用 Redis 后 SSE 照样能工作；反而 SSE 让网关侧无需 sticky、更容易水平扩容。K8s 下的两种路线：会话亲和（简单但扩容不灵活）vs 外部广播（推荐）。另外注意 Redis Pub/Sub 不持久，要做回放得用 Stream（XADD/XRANGE）。
  > **🔗 延伸**
  > 可提「事件溯源的复用价值」：同一套事件流还可喂给审计、重放调试、以及离线评测（回放真实轨迹做回归），一举三得。

## Agent 基础与运行循环

- **Agent 的运行流程是什么？如何理解 RAG 库和 Agent Skill？** —— 感知→规划→工具调用→观察→循环的基本闭环，以及外部知识/技能与模型本身的边界。出处：[[20-Areas/实习与求职/面试题与经验/AI-Agent与大模型岗位面经汇总-01至05-07-08|汇总A·面经02]]

- **如何设计 Agent 循环执行？** —— 循环终止条件、最大轮数、状态推进。出处：[[20-Areas/实习与求职/面试题与经验/AI-Agent开发岗位面经汇总-2026年4月-01至07|汇总B·面经04]]
- **Agent 执行循环如何判断是否需要进入下一个循环？**（🔥）—— 终止判断：任务完成信号、工具无返回、轮数上限。出处：[[20-Areas/实习与求职/面试题与经验/AI-Agent开发岗位面经汇总-2026年4月-01至07|汇总B·面经03]]
  > [!success]- ✅ AI 解答 · Q02 · 2026-09-15
  > **🎯 标准答案（面试版）**以 ReAct 循环（thought→action→observation）为例，进入下一轮的判据是『任务未完成且仍有预算』：模型本轮发出了工具调用而没有输出最终答复，Harness 就把工具结果拼回上下文再执行一轮。终止条件四类：模型给出最终答案（不再调用工具，或显式调用 finish/submit）、达到最大轮数或 Token 预算（如 LangGraph 的 recursion_limit）、发生不可恢复错误、用户中断。
  > **📌 要点**
  > - 继续信号 = 本轮存在工具调用；终止信号 = 产出最终文本
  > - 显式 finish 工具比隐式判断更可控、语义更清晰
  > - 轮数 / Token / 成本三重预算兜底
  > - 异常终止：工具连续失败、同一调用反复出现需熔断
  > **🔬 原理深入**
  > 完成判断本质是 Harness 与模型之间的协议设计：隐式判断（无工具调用即完成）实现简单，但可能被模型『忘写工具调用』误触发；显式 finish 动作语义清晰。工程上还要防两类病态循环：原地打转（同工具同参数反复调用，需 streak 检测熔断）与目标漂移（每轮重申目标、校验产出相关性）。
  > **🔗 延伸**
  > 可追问 LangGraph 的 State/checkpoint 如何支撑循环中断恢复、human-in-the-loop 断点加在哪里。
- **举一个复杂例子，完整串联 Agent 执行过程。** —— 用自己项目（Morrow / AstrBot）完整讲一遍输入到输出。出处：[[20-Areas/实习与求职/面试题与经验/AI-Agent开发岗位面经汇总-2026年4月-01至07|汇总B·面经03]]
  > [!success]- ✅ AI 解答 · Q21 · 2026-09-17
  > **🎯 标准答案（面试版）**面试官要的不是通用流程图，而是你项目里的真实链路。以多 Agent 研究助手为例：用户输入『调研某技术选型』→ 主 Agent（supervisor）先澄清意图、拆解为检索/对比/总结三个子任务 → 分派给子 Agent 并行执行，每个子 Agent 以 ReAct 方式调用搜索/代码执行工具并产出结构化中间结果 → 主 Agent 汇总、交叉校验、发现缺口再补检索 → 整合成带引用的报告返回。讲清三点即合格：每步的输入输出契约是什么、状态存在哪（State/上下文）、失败怎么处理（重试/降级/人工介入）。
  > **📌 要点**
  > - 建议叙事结构：意图澄清→任务拆解→分派执行→汇总校验→产出
  > - 每个 Agent 讲清：输入输出契约、工具集、上下文范围
  > - 必须主动讲失败路径：工具故障、结果质量差、预算超限
  > - 用自己项目的真实细节，别背通用八股
  > **🔬 原理深入**
  > 复杂例子的价值在于展示 Harness 设计能力：状态放共享 State 还是消息传递、子任务边界怎么划、中间结果如何用 Schema 约束、上下文预算怎么分配。面试官常追问『为什么这么拆』——答案要落到测试性、复用性、错误隔离这些工程维度，而不是『听说多 Agent 好』。
  > **🔗 延伸**
  > 可准备一张自己项目的时序图辅助讲解；对追问最深的环节（如 checkpoint 恢复、工具鉴权）要能下钻到实现细节。
- **Agent 能力是由 Spring AI 框架提供，还是通过 Prompt 控制输出？** —— 框架能力 vs 提示词工程的边界。出处：[[20-Areas/实习与求职/面试题与经验/AI-Agent开发岗位面经汇总-2026年4月-01至07|汇总B·面经04]]
  > [!success]- ✅ AI 解答 · Q22 · 2026-09-17
  > **🎯 标准答案（面试版）**Agent 能力是三层叠加：模型能力是基础（推理与函数调用本身是模型层能力）；框架（Spring AI/LangChain4j）提供确定性工程能力——工具注册与执行、循环控制、状态与记忆管理、重试与观测，这些由代码保证、不依赖 Prompt；Prompt 负责调度与约束模型的不确定行为——角色、策略、输出格式、边界护栏。一句话：框架决定『能做什么』（能力的上下界），Prompt 决定『怎么做、做得稳不稳』。把工具执行、流程控制寄希望于 Prompt 是常见误区——Prompt 只能引导，不能保证。
  > **📌 要点**
  > - 模型能力是基础，函数调用是模型层能力
  > - 框架确定性职责：工具执行、循环、状态、重试、观测
  > - Prompt 职责：行为引导、策略、格式、边界护栏
  > - 反例：『请务必调用工具』式 Prompt 不可靠，工具要靠框架注册
  > **🔬 原理深入**
  > 以 Spring AI 为例：ChatClient + @Tool 注解把 Java 方法注册为工具，框架负责 JSON Schema 生成、请求拼装、响应解析与函数执行，这一层是纯工程；而决策质量（选哪个工具、参数对不对）由模型能力与 Prompt 共同决定。工程共识是『能力工程化、行为提示化』——能写代码确定的，绝不交给概率模型。
  > **🔗 延伸**
  > 可追问 MCP 与框架的关系（MCP 标准化工具接入面，框架仍是执行编排层），以及 Java 系与 Python 系 Agent 框架生态对比。
- **未来 Agent 的发展趋势是什么？** —— 结合 Harness、多 Agent、长时运行等观点准备。出处：[[20-Areas/实习与求职/面试题与经验/AI-Agent与大模型岗位面经汇总-01至05-07-08|汇总A·面经01]]
  > [!success]- ✅ AI 解答 · Q23 · 2026-09-17
  > **🎯 标准答案（面试版）**可从五个方向组织：① 更长时运行——从单轮问答走向分钟/小时级长任务，checkpoint、断点恢复、异步任务管理成为标配；② 更强的 Harness——循环控制、沙箱、评估、护栏等外围工程的价值凸显，模型差距缩小后工程决定体验；③ 多 Agent 协作常态化——supervisor/专家分工，MCP、A2A 等协议走向标准化；④ 上下文工程取代单纯 Prompt 工程——记忆系统、检索、状态管理成为核心议题；⑤ 与软件工程深度融合——Agent 进入 SDLC（编码、评审、运维），从聊天产品变成生产力进程。回答时结合自己项目验证其中一两点，避免空谈趋势。
  > **📌 要点**
  > - 长时运行与可靠性工程（checkpoint/异步/人工介入）
  > - Harness 与评测的重要性上升
  > - 多 Agent 协作与协议标准化（MCP、A2A）
  > - 上下文工程：记忆、检索、状态管理
  > - Agent 与软件工程融合（编码、运维 Agent）
  > **🔬 原理深入**
  > 趋势背后是同一个矛盾——模型的概率性与软件确定性要求的冲突。行业解法是把 Agent 当『新型并发进程』管理：可观测、可测试、可回滚。这也是评测（evals）与护栏成为招聘核心要求的原因：能搭建『让 Agent 可信运行』的基础设施，比会调 Prompt 更稀缺。
  > **🔗 延伸**
  > 可引用 Anthropic《Building Effective Agents》及其多 Agent 研究系统博客表达观点；被追问『你怎么看』时，结合自己踩过的坑谈体会比背趋势更有说服力。

## ReAct 与规划范式

- **ReAct 范式如何实现？ReAct 和 CoT 的区别是什么，分别适用于什么场景？** —— 思考-行动-观察交替 vs 单链推理；工具可用性决定选型。出处：[[20-Areas/实习与求职/面试题与经验/AI-Agent与大模型岗位面经汇总-01至05-07-08|汇总A·面经04]]
- **ReAct 式和 Plan-and-Execute 式的区别？什么情况用哪种？**（🔥）—— 动态探索 vs 先规划后执行；任务确定性、步骤深度、成本。出处：[[20-Areas/实习与求职/面试题与经验/AI-Agent开发岗位面经汇总-2026年4月-01至07|汇总B·面经05]]
  > [!success]- ✅ AI 解答 · Q03 · 2026-09-15
  > **🎯 标准答案（面试版）**ReAct 让推理与行动交替进行，每步基于最新观察动态决策，适合环境不确定、需要边做边看的探索型任务；Plan-and-Execute 先由 Planner 产出完整计划，再交 Executor 逐步执行、必要时 replan，适合可清晰分解、步骤较长的任务，轮数与 Token 成本更低且便于并行。选择依据：确定性高、步骤深、成本敏感选 P&E；不确定性高、需要试错选 ReAct。
  > **📌 要点**
  > - ReAct 动态适应强，但轮数多、易目标漂移
  > - P&E 全局结构好、可并行，但计划会过期，必须有 replan
  > - 混合式：先粗规划，执行中偏差触发重规划
  > **🔬 原理深入**
  > 两者本质是『决策时机』的权衡：ReAct 把决策摊到每一步（信息最新但缺全局优化），P&E 一次性全局规划（结构完整但适应性差）。P&E 的经典坑是最初计划建立在假设之上，执行中发现事实不符就必须引入 reflection/replan 节点补救。出处：ReAct（arXiv:2210.03629, Yao et al.）、Plan-and-Solve（arXiv:2305.04091, Wang et al.）。
  > **🔗 延伸**
  > 可聊 LangGraph 官方 plan-and-execute 模板的实现、replan 的触发条件设计。

## Single-Agent vs Multi-Agent 🔥

- **Multi-Agent 的设计逻辑？每个 Agent 是否都有大模型调用？** 出处：[[20-Areas/实习与求职/面试题与经验/AI-Agent与大模型岗位面经汇总-01至05-07-08|汇总A·面经03]]
- **多 Agent 如何进行区分？Trade-off 是什么？** —— 职责拆分维度：功能、阶段、角色；成本/延迟/一致性权衡。出处：[[20-Areas/实习与求职/面试题与经验/AI-Agent与大模型岗位面经汇总-01至05-07-08|汇总A·面经03]]
- **Multi-Agent 和 Single-Agent 各自适合什么场景？**（🔥）—— 出处：[[20-Areas/实习与求职/面试题与经验/AI-Agent与大模型岗位面经汇总-01至05-07-08|汇总A·面经04]]、[[20-Areas/实习与求职/面试题与经验/AI-Agent开发岗位面经汇总-2026年4月-01至07|汇总B·面经02]]
  > [!success]- ✅ AI 解答 · Q04 · 2026-09-15
  > **🎯 标准答案（面试版）**Single-Agent 用一个模型配丰富工具完成任务，上下文连贯、调试简单、成本低，适合职责单一、流程线性的场景；Multi-Agent 把任务分给多个角色（planner/researcher/critic 等），每个 Agent 拥有独立上下文，带来专业化分工、上下文隔离与并行加速，适合子任务边界清晰、单上下文装不下或需要对抗校验的复杂工作流。原则：单 Agent 能解决就不要上多 Agent。
  > **📌 要点**
  > - 多 Agent 的真实收益是上下文隔离与专业化，不是『更聪明』
  > - 代价：通信开销、误差逐层传播、状态一致性难、调试困难
  > - 折中形态：supervisor 路由、子任务分派、critic 校验节点
  > **🔬 原理深入**
  > Anthropic 多 Agent 研究系统报告显示，多 Agent 在广度型研究任务上明显优于单 Agent，但 Token 消耗约为其 15 倍，因此只在任务价值足够高时启用。误差传播是多 Agent 的核心风险，要求每一层都有验证节点，否则一个 Agent 的幻觉会被下游放大。
  > **🔗 延伸**
  > 可对比 AutoGen（对话式）、CrewAI（角色制）、LangGraph（图编排）三种组织方式的适用场景。
- **多 Agent 之间如何分工协作？** 出处：[[20-Areas/实习与求职/面试题与经验/AI-Agent开发岗位面经汇总-2026年4月-01至07|汇总B·面经02]]
  > [!success]- ✅ AI 解答 · Q25 · 2026-09-17
  > **🎯 标准答案（面试版）**分工有三种主流切法：按功能角色（planner/executor/critic/summarizer）、按流程阶段（检索→抽取→汇总）、按领域专长（代码/文档/数据专家）。协作模式从松到紧：① supervisor 主从式——主 Agent 拆解分派、汇总校验，可控性最好、最常用；② 流水线式——按阶段串行传递，结构清晰；③ 对话/辩论式——Agent 互评对抗提升质量，成本最高。协作的关键工程问题是接口契约：每个 Agent 的输入输出用结构化格式（JSON Schema）约束，避免自然语言传话造成信息丢失与格式漂移。
  > **📌 要点**
  > - 三种分工维度：功能角色 / 流程阶段 / 领域专长
  > - supervisor 主从式最常用：拆解→分派→汇总→校验
  > - 对抗式（critic/辩论）提升质量但成本高
  > - 接口契约（结构化 IO）比协作形式更重要
  > **🔬 原理深入**
  > 分工的本质是上下文工程：让每个 Agent 只持有它需要的上下文（隔离带来专注与省 Token），用共享黑板/State 传递必要中间结果。Anthropic 多 Agent 研究系统采用 orchestrator-worker 模式：lead agent 拆任务、并行派发、汇总引用，Token 约为单 Agent 15 倍，但广度型研究任务收益显著——分工要在收益与开销间算账。
  > **🔗 延伸**
  > 可准备失败案例：边界模糊导致职责重叠、误差逐层传播时多 Agent 反而更差；可对比 LangGraph supervisor 模板与 CrewAI 角色制的实现差异。
- **Multi-Agent 如何共享上下文？子 Agent 是否会使用父 Agent 的全部 Context？** —— 共享黑板 vs 消息传递；上下文裁剪。出处：[[20-Areas/实习与求职/面试题与经验/AI-Agent开发岗位面经汇总-2026年4月-01至07|汇总B·面经05]]
  > [!success]- ✅ AI 解答 · Q26 · 2026-09-17
  > **🎯 标准答案（面试版）**主流做法是『裁剪传递』而非全量共享：父 Agent 不下发全部 Context，而是按子任务提炼任务简报（目标、相关事实、输出格式约束）传给子 Agent；子 Agent 在独立上下文里执行，产出结构化结果回传。共享机制三种：① 消息传递式——简报进、结果出，隔离最好、最常用；② 共享黑板/State 式——如 LangGraph 共享 State 对象，节点读写公共字段，适合需要全局状态一致性的编排；③ 外部存储式——落盘共享工作区各自读写，适合长任务与产物交接。子 Agent 默认不应看到父 Agent 全部上下文：Token 成本、无关信息干扰（lost-in-the-middle）、权限与安全边界三个原因。
  > **📌 要点**
  > - 默认裁剪传递：任务简报进，结构化结果出
  > - 三种机制：消息传递 / 共享 State / 外部存储
  > - 全量共享代价：Token 爆炸 + 干扰 + 越权风险
  > - 需要全局视图时用共享 State，注意并发写合并
  > **🔬 原理深入**
  > 本质是把上下文当作分层记忆：父 Agent 的 Context 是规划层，子 Agent 只拿『完成该任务的最小充分信息』，类似最小权限原则。简报质量直接决定子 Agent 产出——要包含目标、已知事实、输出契约与边界，但不要带父层的推理噪声；结果回传时带出处与置信度，方便父 Agent 交叉校验。
  > **🔗 延伸**
  > 可追问 LangGraph 子图如何共享 State（schema 合并、字段覆盖与 reducer 策略），以及子 Agent 失败时父 Agent 的重派策略。

## 工作流与状态机

- **什么是对抗式状态机？** 出处：[[20-Areas/实习与求职/面试题与经验/AI-Agent与大模型岗位面经汇总-01至05-07-08|汇总A·面经04]]
  > [!success]- ✅ AI 解答 · Q27 · 2026-09-17
  > **🎯 标准答案（面试版）**对抗式状态机是在状态流转中引入『生成方与检验方相互对抗』的机制：某状态由生成角色驱动（产出方案/内容），转移条件由对抗角色把关（审查、质疑、测试），不通过则打回重做，通过才进入下一状态。典型形态：drafter↔reviewer 循环、planner↔critic、红蓝对抗（一个 Agent 完成任务，另一个专门找茬）。价值是把质量检查内建到状态机里，用对抗压力换产出可靠性；代价是轮数与 Token 翻倍，必须设收敛控制——最大轮数、评分阈值、连续通过 N 次提前放行——防止无限对抗。
  > **📌 要点**
  > - 核心：状态转移由检验方把关，不通过就打回
  > - 常见形态：drafter-reviewer、planner-critic、红队蓝队
  > - 收敛控制：最大轮数、阈值、提前通过条件
  > - 代价：Token 与延迟上升，按任务价值选用
  > **🔬 原理深入**
  > 思想源自 GAN 的对抗训练与辩论式对齐（AI Safety via Debate, arXiv:1805.00899）：独立对抗视角能暴露单模型自我审查的盲区。同一个模型既当运动员又当裁判存在自我一致性偏差，所以检验方通常用不同 Prompt 甚至不同模型实例化，保证评价独立性；打回重做时要携带评审意见，否则生成方只会重复原错误。
  > **🔗 延伸**
  > 可追问 LangGraph 实现（critic 节点条件边回跳 + State 中累积重试计数）；可对比 self-reflection——反思是自我迭代，对抗式是独立角色互查，更贵但更客观。
- **状态机和流式处理有什么区别，分别在什么时候使用？** 出处：[[20-Areas/实习与求职/面试题与经验/AI-Agent与大模型岗位面经汇总-01至05-07-08|汇总A·面经04]]
  > [!success]- ✅ AI 解答 · Q28 · 2026-09-17
  > **🎯 标准答案（面试版）**状态机是『离散步骤』模型——系统在有限状态间按转移条件跳转，每步有明确前置状态与产出，适合流程结构清晰、需要严格控制与可回溯的场景（审批流、任务编排、Agent 阶段化执行）。流式处理是『连续数据』模型——数据持续到达、边到边处理、无步骤边界，适合实时性优先的场景（LLM token 流式输出、日志管道、消息推送）。二者不互斥：Agent 系统常见组合是外层状态机管阶段（规划→执行→汇总），节点内部对流式输出做增量处理。选择标准：关心『流程走到哪一步、可否回滚』用状态机；关心『数据多快被处理/呈现』用流式。
  > **📌 要点**
  > - 状态机：离散、可控、可回溯，适合编排与审批逻辑
  > - 流式：连续、低延迟、无边界，适合 token 流与数据管道
  > - 实践组合：外层状态机 + 节点内流式输出
  > - 状态机要处理异常转移；流式要处理乱序与背压
  > **🔬 原理深入**
  > 二者在 LLM 应用中的交汇是体验与可靠性的平衡：流式把首 token 延迟降到毫秒级感知，但流式内容要进状态（State）就必须区分『未提交』与『已提交』——流没有终结符前，State 里的值只可用于展示、不可作为后续节点的决策依据，工程上要加完整性校验，避免半截输出被下游消费。
  > **🔗 延伸**
  > 可追问 LangGraph 的 stream_mode（values/updates/messages）如何同时支持状态推进与流式输出，以及 SSE 与 WebSocket 的选型依据。
- **工作流解决什么问题，用户是谁？** 出处：[[20-Areas/实习与求职/面试题与经验/AI-Agent与大模型岗位面经汇总-01至05-07-08|汇总A·面经04]]
  > [!success]- ✅ AI 解答 · Q29 · 2026-09-17
  > **🎯 标准答案（面试版）**工作流解决的是『把不确定的模型行为装进确定的业务流程』：固定步骤、明确每步输入输出、在关键点嵌入模型调用，让整体流程可预测、可测试、可审计、可回滚。它用灵活性换可靠性，适合错误代价高、路径可预知的业务（审批、风控、文档处理、客服工单）。用户分两类：直接用户是业务角色（运营、审核、客服，要的是稳定可用）；构建用户是工程团队（要的是可编排、可观测、可迭代的开发体验）。与自由 Agent 的分界：路径可枚举用工作流，开放探索用 Agent；生产系统常用混合式——工作流做骨架、Agent 做弹性节点。
  > **📌 要点**
  > - 本质：用确定性框架约束概率性模型
  > - 收益：可预测、可测试、可审计、可回滚
  > - 直接用户=业务角色；构建用户=工程团队
  > - 分界：路径可枚举→工作流，开放探索→Agent
  > **🔬 原理深入**
  > Anthropic《Building Effective Agents》的表述是：能用 workflow 就别用 agent——workflow 用代码定义流程，可预测且成本低；agent 自主决策路径，适合开放式任务。生产系统多数是混合形态：核心链路固定不变，局部开放环节交给 Agent 自主。LangGraph 这类框架同时提供两种抽象，正是为了支持这种混合架构。
  > **🔗 延伸**
  > 可结合自己项目说明哪段是固定工作流、哪段交给 Agent 自主，以及这么划的理由（错误代价、路径可枚举性）。
- **工作流延迟是否较高，如何解决？** —— 并行节点、缓存、流式中间输出。出处：[[20-Areas/实习与求职/面试题与经验/AI-Agent与大模型岗位面经汇总-01至05-07-08|汇总A·面经04]]
  > [!success]- ✅ AI 解答 · Q30 · 2026-09-17
  > **🎯 标准答案（面试版）**会——多节点工作流把延迟叠加为各节点之和，其中 LLM 调用是大头（秒级），串行节点越多越明显。优化按性价比排序：① 并行化——无依赖节点 fan-out/fan-in 并发执行，收益最大；② 缓存——检索结果与相同输入的 LLM 调用直接命中；③ 流式中间输出——先推送已就绪部分改善体感；④ 模型分级——简单节点换小模型；⑤ 精简上下文与输出 Token；⑥ 非实时链路异步化，用通知回报。工程上先测各节点耗时分布，再对症下药，避免过早优化。
  > **📌 要点**
  > - 延迟=各节点之和，LLM 调用是大头
  > - 并行化收益最大：无依赖节点 fan-out
  > - 缓存、流式推送、模型分级、Token 精简、异步化
  > - 先做节点级耗时测量，再优化关键路径
  > **🔬 原理深入**
  > Amdahl 定律在此适用：加速比受限于必须串行的部分，所以要优先压缩关键路径——把关键路径上的节点并行化或换小模型才有效，非关键路径的优化对总延迟无感。另外要区分『体感延迟』与『完成延迟』：流式输出决定前者（用户体验），全链路完成时间决定后者（吞吐与成本），二者的优化手段不同。
  > **🔗 延伸**
  > 可追问 LangGraph 并行节点的 State 合并策略（字段级 reducer 解决并发写冲突），以及长尾节点（偶发超时）的超时与降级设计。
- **组件可插拔是什么意思？** 出处：[[20-Areas/实习与求职/面试题与经验/AI-Agent与大模型岗位面经汇总-01至05-07-08|汇总A·面经04]]
  > [!success]- ✅ AI 解答 · Q31 · 2026-09-18
  > **🎯 标准答案（面试版）**指 Agent 系统里每个环节——模型、工具、检索器、记忆、编排策略——都通过统一接口接入，可以独立替换升级而不牵动整条链路。例如换 LLM 只改 provider 配置，换向量库只换 retriever 实现，工具层换成 MCP 服务后插拔粒度从「函数」升级到「服务」。
  > **📌 要点**
  > - 接口抽象是前提：Function Calling/MCP 工具协议、模型 provider 统一接口
  > - 配置驱动装配，业务代码只依赖抽象而非具体实现
  > - 收益：试错成本低、不被供应商锁定、A/B 对比容易
  > **🔬 原理深入**
  > 实现靠依赖注入+适配层：各组件实现同一协议（如 Runnable / tool schema），运行时按配置装配。代价是抽象层带来间接性与调试深度，过度抽象会让链路问题定位变难，常见折衷是「接口收敛、实现从简」。
  > **🔗 延伸**
  > 面试加分点是结合项目讲「哪一层真的换过、换了什么、踩了什么坑」，并准备好被追问抽象层性能损耗怎么办。

## LangGraph：State、子图与 Checkpoint 🔥

- **LangGraph 中三个子图如何传递数据？** —— State 机制、`StateGraph`/`add_node`/`add_edge`，节点读改写 State。出处：[[20-Areas/实习与求职/面试题与经验/小红书-Agent开发实习生-一面面经-AIGC小白入门记|小红书·AIGC小白入门记]]
- **为什么拆成三个子图，而不是一条 Pipeline？**（🔥）—— 测试性、复用性、扩展性、错误隔离四维对比。出处：[[20-Areas/实习与求职/面试题与经验/小红书-Agent开发实习生-一面面经-AIGC小白入门记|小红书·AIGC小白入门记]]、[[20-Areas/实习与求职/面试题与经验/小红书Agent开发实习生一面-百度Agent面经-杰尼龟|小红书/百度·杰尼龟]]
  > [!success]- ✅ AI 解答 · Q05 · 2026-09-15
  > **🎯 标准答案（面试版）**（结合项目）拆成三个子图（采集→分析→质检修订）主要出于四点：测试性——每个子图可独立运行、独立构造测试数据，回归成本低；复用性——子图通过明确的 State 接口对外服务，其它流程可直接挂载；扩展性——替换某子图内的模型或节点不影响其余部分，还能按阶段选型（采集用便宜模型、分析用强模型）；错误隔离——失败的重试与回滚限定在子图内，checkpoint 粒度更细，不必整体重跑。
  > **📌 要点**
  > - 子图 = 独立 State schema + 独立 checkpoint 边界
  > - 接口清晰：父子图通过输入输出 State 映射通信
  > - 故障半径小：失败定位与恢复都限定在阶段内
  > **🔬 原理深入**
  > 一条大 Pipeline 的问题在于所有节点共享一个巨型 State，字段高度耦合，改一个字段可能牵连全链；而 LangGraph 的子图本质是『把图当节点』的组合，父图只关心子图的输入输出契约，内部实现可以自由演进。
  > **🔗 延伸**
  > 可继续聊 human-in-the-loop 断点为什么放在子图边界、如何用 LangGraph Studio 分子图调试。
- **子图为什么要放多个小节点？为什么结合 LangGraph 和子 Agent，而不是一个大 Agent 或脚本？** 出处：[[20-Areas/实习与求职/面试题与经验/小红书Agent开发实习生一面-百度Agent面经-杰尼龟|小红书/百度·杰尼龟]]
  > [!success]- ✅ AI 解答 · Q32 · 2026-09-18
  > **🎯 标准答案（面试版）**拆成小节点让每一步都有独立的状态写入、错误边界与可观测性：LangGraph 里每个节点执行都会产生 checkpoint 和流式更新，出问题能定位到具体步骤；塞进一个大 Agent 的单次循环则中途黑盒、失败只能整体重跑。LangGraph 负责确定性的流程骨架（结构、状态、断点），子 Agent 负责需要自主决策的开放环节——纯脚本做不了动态决策，纯大 Agent 又不可控，二者组合是「结构化+灵活性」。
  > **📌 要点**
  > - 小节点 = 细粒度 checkpoint、精准错误隔离、可单测
  > - 大 Agent 的 recursion_limit 只是粗糙保险丝，黑盒循环难回放
  > - 图骨架管确定性流程，子 Agent 管开放性决策
  > **🔬 原理深入**
  > LangGraph 节点是 State→State 的准纯函数变换，天然可测试；子 Agent 本身是一个封装好的 compiled graph，可作为父图节点嵌套，通过输入输出 Schema 与父 State 对接。粒度边界选在「决策点」上：把分支判断做成节点，把决策执行交给子 Agent。
  > **🔗 延伸**
  > 可主动讲反例：粒度过细会让编排复杂度爆炸、State 字段膨胀，合适的做法是先粗后细，哪里出问题拆哪里。
- **AI 节点的输入和输出如何对接？上下文/数据如何在节点之间传递？** 出处：[[20-Areas/实习与求职/面试题与经验/小红书Agent开发实习生一面-百度Agent面经-杰尼龟|小红书/百度·杰尼龟]]
  > [!success]- ✅ AI 解答 · Q33 · 2026-09-18
  > **🎯 标准答案（面试版）**LangGraph 用共享 State 做唯一数据总线：节点把当前 State 作为输入，返回对部分字段的新值，框架按字段 reducer 合并写入，下一个节点读到的就是合并后的新 State。工具结果、检索数据写进 State 的指定字段；LLM 节点从 State 挑字段组装 prompt、输出经解析器写回。跨子图则通过输入/输出 Schema 显式映射传递。
  > **📌 要点**
  > - State 是唯一事实源，节点间不私下传变量
  > - 节点返回增量更新，同字段并发写靠 reducer（如 add_messages 追加）
  > - 跨子图：input/output Schema 映射，避免父图内部结构泄漏
  > **🔬 原理深入**
  > State 一般用 TypedDict/Pydantic 定义，字段用 Annotated 挂 reducer，并行节点在同一 super-step 结束后统一合并，因此并发写是确定性的。Checkpoint 存每步快照，所谓「传递」本质是快照序列的演进，可回放调试。
  > **🔗 延伸**
  > 可聊大对象（长文档、图片）不直接进 State 而是外置存储、State 只放引用，否则每步快照成本高、上下文易爆。
- **子图中的某个节点是否可以重复运行？子图是否可以独立运行？** 出处：[[20-Areas/实习与求职/面试题与经验/小红书Agent开发实习生一面-百度Agent面经-杰尼龟|小红书/百度·杰尼龟]]
  > [!success]- ✅ AI 解答 · Q34 · 2026-09-18
  > **🎯 标准答案（面试版）**都可以。节点重复运行的三种来源：失败自动重试（RetryPolicy）、human-in-the-loop 的 interrupt 后恢复重放、条件边回跳形成的循环，每次执行都有独立 checkpoint，因此副作用节点要自己保证幂等。子图独立运行：compile 后的子图就是可独立 invoke 的图，可以单测、调试、单独部署，也能作为节点嵌入父图，独立运行时自备初始 State 与 checkpointer。
  > **📌 要点**
  > - 重试 ≠ 整链重跑：从该节点前的 checkpoint 恢复
  > - interrupt/resume 让节点可暂停后继续
  > - 循环回跳要加计数上限（如最多重写 N 次），防死循环
  > **🔬 原理深入**
  > LangGraph 按 super-step 执行并在每步后持久化，节点重试等价于重放该 step，所以「读类节点可随意重试、写类节点要幂等或补偿」。父图嵌入子图时 thread_id 上下文由父图管理，Studio 里也能分子图调试。
  > **🔗 延伸**
  > 面试可举「审稿节点被打回重写」的例子：重写次数写进 State 作为条件边判据，超限走人工介入分支。
- **在 LangGraph 基础上是否做过上层路由决策（AI 判断走哪个节点）？** —— 动态路由 vs 固定边。出处：[[20-Areas/实习与求职/面试题与经验/小红书Agent开发实习生一面-百度Agent面经-杰尼龟|小红书/百度·杰尼龟]]
  > [!success]- ✅ AI 解答 · Q35 · 2026-09-18
  > **🎯 标准答案（面试版）**常见做法是「路由节点 + 条件边」：一个 LLM 节点读取 State，输出结构化决策（如 enum 的下一节点名或意图标签），add_conditional_edges 按输出映射分支；更动态的场景用 Send API 在运行时把任务分发到任意节点或并行扇出（map-reduce）。原则是 AI 只做决策、框架执行路由，非法值由图约束和默认分支兜底。
  > **📌 要点**
  > - 路由输出必须结构化（enum/JSON Schema）并校验
  > - Send API 支持运行时动态分支与扇出
  > - 固定边管确定性流程，条件边管语义路由，分层使用
  > **🔬 原理深入**
  > 路由错误是长链路误差放大器：工程上要做三件事——输出约束（ constrained decoding 或枚举校验）、非法值防御（默认分支/重问）、路由决策写进 State 留痕供审计。图级路由相比节点内 if-else 的优势是每个分支有独立 checkpoint 与可观测性。
  > **🔗 延伸**
  > 可聊低置信度场景：路由模型不确定时先走澄清节点再决策，或用小模型粗路由+大模型确认来省成本。
- **State 管理和 Checkpoint 机制为什么是核心，而不只是工程细节？** —— 可恢复、可回放、可审计。出处：[[20-Areas/实习与求职/面试题与经验/AI-Agent开发岗位面经汇总-2026年4月-01至07|汇总B·面经07]]
  > [!success]- ✅ AI 解答 · Q36 · 2026-09-18
  > **🎯 标准答案（面试版）**因为生产级长链路 Agent 的可靠性完全建立在这两者上：State 定义了系统内部的数据契约，Checkpoint 把每次演进落盘。故障时从最近快照恢复而非整链重跑，这是可恢复；完整的快照序列支持回放定位与回归测试，这是可回放；每一步输入输出留痕，这是可审计。没有它们，Agent 只能跑 demo 不能上生产，所以是核心能力而非工程细节。
  > **📌 要点**
  > - 可恢复：宕机/失败从 checkpoint 续跑
  > - 可回放：时间旅行调试、改参数后从中间步重跑
  > - 可审计：每步状态与决策留痕，满足排查与合规
  > **🔬 原理深入**
  > LangGraph checkpointer 按 (thread_id, step) 持久化 channel values 和 pending writes，后端可选 SQLite/Postgres 等；时间旅行通过 get_state_history 取历史快照、修改后重跑实现。恢复语义是「重放待执行节点」，副作用节点需幂等或补偿设计。
  > **🔗 延伸**
  > 可聊权衡：checkpoint 越频繁恢复粒度越细但 IO 越重；以及落盘数据的敏感信息脱敏与保留策略。
- **LangGraph 的 Checkpoint 和 Memory 到底有什么区别？** —— 断点持久化 vs 长期记忆语义。出处：[[20-Areas/实习与求职/面试题与经验/AI-Agent开发岗位面经汇总-2026年4月-01至07|汇总B·面经07]]
  > [!success]- ✅ AI 解答 · Q37 · 2026-09-18
  > **🎯 标准答案（面试版）**Checkpoint 是执行层概念：某个 thread（一次会话/一次任务）内每一步 State 的持久化快照，用途是恢复、回放，随 thread 生命周期管理；Memory 是记忆层概念：跨 thread 的长期信息（LangGraph 的 Store），比如用户偏好、事实画像，按命名空间组织、支持语义检索，不依附于某次运行。一句话：Checkpoint 管「这次跑到哪、状态是什么」，Memory 管「关于用户和世界我知道什么」。
  > **📌 要点**
  > - Checkpoint：thread 内、step 级、框架自动产生
  > - Memory（Store）：跨 thread、命名空间组织、显式读写
  > - 易混点：多轮对话上下文是 checkpoint 产物，不是长期记忆
  > **🔬 原理深入**
  > 实现上 checkpointer 存的是每个 super-step 的通道值与待写事务；Store 是键值+向量混合存储，节点内显式 put/get/search，可为内容建索引启用 semantic search。二者可以联动：节点执行时从 Store 检索长期记忆注入 State。
  > **🔗 延伸**
  > 可聊记忆写入策略（什么值得记、去重合并、遗忘机制），对比 mem0、Letta/MemGPT 的方案差异。
- **对话执行中出现状态竞争问题时，通常如何解决？** —— 并发写 State、锁/队列/不可变更新。出处：[[20-Areas/实习与求职/面试题与经验/AI-Agent开发岗位面经汇总-2026年4月-01至07|汇总B·面经07]]
  > [!success]- ✅ AI 解答 · Q38 · 2026-09-18
  > **🎯 标准答案（面试版）**分两层看。图内并发：LangGraph 并行节点在同一 super-step 执行，写同一字段由字段级 reducer 决定合并策略（追加/覆盖/自定义），并发写在框架层就是确定性的，不需要自己加锁；跨请求或跨进程：对共享的外部资源才用乐观锁（版本号）、消息队列串行化或按 thread_id 分区。原则是能靠 reducer 解决的不上锁，State 更新尽量不可变追加，必须加锁时粒度最小化。
  > **📌 要点**
  > - 字段级 reducer 是图内并发标准解（如 operator.add 收集扇出结果）
  > - 副作用写外部系统才需要幂等键、行锁、队列
  > - 不可变更新+显式合并，避免读-改-写竞态
  > **🔬 原理深入**
  > LangGraph 采用 Pregel 风格执行：并行节点更新先收集、super-step 结束统一按 channel reducer 应用，所以「同时写 State」本身不会撕裂。真正的竞争发生在节点内对外部系统的副作用，比如两个并行节点写同一张表，要用幂等键或把写操作收敛到一个汇聚节点。
  > **🔗 延伸**
  > 可被追问跨 thread 的 Store 并发写：目前近似 last-write-wins，重要记忆要做版本与时间戳仲裁。
- **如果任务失败（如数据获取为空），整个工作流如何设计恢复逻辑？** —— 重试、降级、人工介入、Checkpoint 回滚。出处：[[20-Areas/实习与求职/面试题与经验/AI-Agent开发岗位面经汇总-2026年4月-01至07|汇总B·面经07]]
  > [!success]- ✅ AI 解答 · Q39 · 2026-09-18
  > **🎯 标准答案（面试版）**按失败类型分层恢复：瞬时故障（网络抖动）用节点级 RetryPolicy 指数退避重试；数据质量问题（结果为空、低质）走条件边降级分支——换数据源、缩小检索范围、返回兜底内容；不可恢复或高风险场景用 interrupt 转人工，审批后 resume；严重时从 checkpoint 回滚到上游重跑，而不是从零开始。失败计数与降级标记写进 State，超限熔断并告警。
  > **📌 要点**
  > - 空结果也是信号：区分「真没数据」和「查询方式错了」
  > - 节点分类设计：查询类可重试、写入类要补偿、外部依赖要降级
  > - 每次恢复都基于 checkpoint，上下文不丢
  > **🔬 原理深入**
  > 工程上先做失败模式清单：给每类失败定义恢复语义和预算（重试次数、时间上限），条件边根据 State 里的 failure_count 路由到 fallback 节点；多次失败的任务落死信表待人工处理，这就是把 SRE 的错误预算思路搬进 Agent。
  > **🔗 延伸**
  > 可聊实际案例：检索为空时先做查询改写重试一次，仍空则回退到通用知识作答并明确标注来源缺失。
- **是否使用过 LangChain？它的优点是什么？** 出处：[[20-Areas/实习与求职/面试题与经验/AI-Agent与大模型岗位面经汇总-01至05-07-08|汇总A·面经04]]
  > [!success]- ✅ AI 解答 · Q40 · 2026-09-18
  > **🎯 标准答案（面试版）**用过。LangChain 的核心价值是组件标准化：统一的多 provider 模型接口（换模型基本零成本）、覆盖文档加载/切分/向量化/检索/输出解析的现成生态、以及 LCEL 声明式管道（天然支持流式、异步、批量）。原型速度快、社区方案多。同时要诚实讲边界：早期 AgentExecutor 黑盒重，复杂编排现在首选 LangGraph（同属 LangChain 生态），LangChain 更多当「组件库+接口标准」用。
  > **📌 要点**
  > - 统一 Runnable 接口：invoke/batch/stream 全组件一致
  > - Loader→Splitter→Embedder→VectorStore→Retriever 每层可替换
  > - 定位：轻编排+组件生态，复杂图编排交给 LangGraph
  > **🔬 原理深入**
  > LCEL 用 Runnable 协议让组合子透明获得流式与重试能力；工程上常见的落地如 RecursiveCharacterTextSplitter 配多路召回解决召回率、OutputParser 约束结构化输出。面试落到具体案例比背优点有说服力。
  > **🔗 延伸**
  > 可聊从 AgentExecutor 迁移 LangGraph 的收益（状态可控、可断点续跑），以及对框架锁定风险的看法（接口抽象层自留一套）。

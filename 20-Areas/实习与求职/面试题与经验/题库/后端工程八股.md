## Java 集合与语法 🔥

- **HashMap 相关八股**（🔥）—— 底层结构、扩容机制、树化阈值。出处：[[20-Areas/实习与求职/面试题与经验/AI-Agent与大模型岗位面经汇总-01至05-07-08|汇总A·面经05]]、[[20-Areas/实习与求职/面试题与经验/AI-Agent开发岗位面经汇总-2026年4月-01至07|汇总B·面经02]]
  > [!success]- ✅ AI 解答 · Q10 · 2026-09-15
  > **🎯 标准答案（面试版）**JDK8 的 HashMap 底层是数组+链表+红黑树。put 时对 key 做 hash 扰动（高 16 位异或低 16 位），再用 (n-1)&hash 定位桶；冲突挂链表（尾插）；链表长度达到 8 且数组容量 ≥64 时树化为红黑树（否则优先扩容），查询从 O(n) 降为 O(log n)；默认容量 16、负载因子 0.75，size 超过阈值触发翻倍扩容并重新分布元素。线程不安全，并发用 ConcurrentHashMap（JDK8 为 CAS + synchronized 锁桶头节点）。
  > **📌 要点**
  > - 容量恒为 2 的幂：(n-1)&hash 位运算代替取模
  > - 树化条件：链长 8 且容量 64；退化阈值 6
  > - 负载因子 0.75 是时间与空间的折中
  > - JDK7 头插并发扩容会成环，JDK8 改尾插
  > **🔬 原理深入**
  > 树化阈值 8 源自泊松分布——负载因子 0.75 时单桶链长达 8 的概率约千万分之一，树化是极端冲突的兜底而非常规路径；hash 扰动 (h ^ h>>>16) 让高位参与索引减少聚集；扩容时 JDK8 按 (hash & oldCap) 把桶拆成高低位两条链，无需逐个重算 hash。
  > **🔗 延伸**
  > 高频追问：为什么线程不安全（覆盖丢失、扩容丢数据）、ConcurrentHashMap 1.7 分段锁与 1.8 CAS 的演进、HashMap/LinkedHashMap/TreeMap 选型。
- **HashMap 严重哈希冲突、转红黑树后删除元素，什么情况退回链表？是直接转换吗？** —— 退化阈值 6 且节点数要求，渐进转换。出处：[[20-Areas/实习与求职/面试题与经验/AI-Agent开发岗位面经汇总-2026年4月-01至07|汇总B·面经02]]
  > [!success]- ✅ AI 解答 · Q83 · 2026-09-23
  > **🎯 标准答案（面试版）**：不是直接转换，是带条件的渐进退化。两个触发点：①删除节点时，removeTreeNode 判断树已足够小（root 左右子树连环 null 判断，近似节点数 ≤ 6）就 untreeify 退回链表；②扩容 split 时，一条树链按 hash 高位拆成两个桶，拆完长度 ≤ UNTREEIFY_THRESHOLD(6) 的桶退回链表。
  > **📌 要点**
  > - 树化前提：链表长度 ≥ 8 且 table 容量 ≥ 64，否则只扩容不树化
  > - 退化阈值 6 < 树化阈值 8：留 2 的缓冲，防止 8/6 边界频繁互转抖动
  > - 删除路径：removeTreeNode 里 O(1) 的树高近似判断（root.left.left == null 等）
  > - 扩容路径：resize 的 split 按高低位拆桶后，binCount ≤ 6 → untreeify
  > **🔬 原理深入**：为什么删除不设「退到 8 才转」？因为退化判定看的是树高而非节点数：红黑树高度约 2*log2(n)，n=6 时高约 5，查询收益已与链表相差无几，维持红黑着色与旋转的成本反而占优。removeTreeNode 的连环 null 判断就是在常数时间内近似回答「这棵树是否只有两层」。resize 拆桶是 HashMap 最常见的退化来源：一条 10 节点的树链拆完常常一边不足 6 个，自然回退。
  > **🔗 延伸**：追问：为什么树化阈值是 8？（泊松分布下理想散列桶长到 8 的概率约千万分之一，树化是 hash 瘾坏/攻击的兜底而非常态）
- **使用 Java 几？新版本虚拟线程有什么特性？** —— Java 21 虚拟线程：轻量、挂起不阻塞平台线程。出处：[[20-Areas/实习与求职/面试题与经验/AI-Agent开发岗位面经汇总-2026年4月-01至07|汇总B·面经02]]
  > [!success]- ✅ AI 解答 · Q84 · 2026-09-23
  > **🎯 标准答案（面试版）**：主力是 Java 8/11/17，并了解 Java 21（LTS）正式落地的虚拟线程（JEP 444）：由 JVM 调度的轻量线程，创建成本 KB 级、阻塞时挂起而不占用操作系统线程，可轻松开百万级并发，特别适合 I/O 密集型高并发服务，代码保持同步写法即获得异步吞吐。
  > **📌 要点**
  > - 版本主线：8（Lambda/Stream）→ 11（LTS）→ 17（LTS，sealed/record）→ 21（LTS，虚拟线程）
  > - 虚拟线程：用户态 M:N 调度，mount 到载体线程（ForkJoinPool）运行
  > - 用法：Thread.ofVirtual().start() 或 Executors.newVirtualThreadPerTaskExecutor()
  > - 使用原则：每任务一线程、不要池化虚拟线程
  > - 注意 pinning：synchronized 块内阻塞会钉住载体线程（JDK 21；JEP 491 在 JDK 24 解决）
  > **🔬 原理深入**：传统线程 1:1 映射 OS 线程，阻塞即浪费一个内核调度单元，高并发只能靠线程池 + 异步编程（CompletableFuture/WebFlux）换吞吐但牺牲可读性。虚拟线程在 JVM 层实现 M:N：调用阻塞 API 时 JVM 把栈帧复制到堆、unmount 载体线程去执行其他虚拟线程，就绪后再 mount 恢复——阻塞对库透明，异步复杂度消失。代价：CPU 密集无收益；pinning 场景（synchronized 内阻塞、native 调用）会退化，旧代码迁移需关注。
  > **🔗 延伸**：追问：虚拟线程 vs 线程池？（池化是为了复用昂贵资源，虚拟线程廉价故每任务一个）vs Go 协程？（JVM 层实现、对现有阻塞 API 透明）

- **手撕 Java：内存泄漏问题** —— 常见泄漏源（静态集合、未关闭资源、ThreadLocal）、排查工具。出处：[[20-Areas/实习与求职/面试题与经验/AI-Agent与大模型岗位面经汇总-01至05-07-08|汇总A·面经02]]
  > [!success]- ✅ AI 解答 · Q86 · 2026-09-23
  > **🎯 标准答案（面试版）**：Java 有 GC 但仍会内存泄漏，本质是「不再使用的对象仍被 GC Root 强可达」。常见泄漏源：静态集合只进不出、资源未关闭、线程池中 ThreadLocal 残留、监听器/回调未注销、内部类持有外部引用。排查路径：先看堆占用趋势确认泄漏特征，再 jmap dump 堆快照，用 MAT 的支配树/Leak Suspects 找到 GC Root 引用链定位代码。
  > **📌 要点**
  > - 静态集合：static Map 缓存只进不出 → 换 WeakHashMap 或 Caffeine 带淘汰
  > - 资源关闭：流/连接统一 try-with-resources
  > - ThreadLocal：线程池线程复用，用完必须 remove()
  > - 监听器/回调：注册与注销成对出现
  > - 排查工具链：jmap -dump → MAT 支配树；jstat -gcutil 看 GC 趋势；Arthas 在线诊断；-XX:+HeapDumpOnOutOfMemoryError 兜底
  > **🔬 原理深入**：先分清「泄漏」与「内存不足」：泄漏的特征是 Full GC 后老年代占用台阶式上涨不回落。ThreadLocal 是线程池经典坑——ThreadLocalMap 的 Entry 对 key 是弱引用、对 value 是强引用，线程不死 value 就一直可达。为什么弱引用救了 key 救不了 value？因为 value 的可达链是 Thread→ThreadLocalMap→Entry→value，这条强引用链不断 GC 就无能为力，所以 remove() 是必须的清理动作而非可选优化。
  > **🔗 延伸**：追问：堆外内存泄漏？（DirectByteBuffer、Netty 引用计数漏 release）元空间泄漏？（cglib/反射动态生成类未卸载）

## Spring 与框架

- **Spring 的 AOP 和 IoC 是什么，如何实现？** —— 动态代理、Bean 生命周期、三级缓存。出处：[[20-Areas/实习与求职/面试题与经验/AI-Agent开发岗位面经汇总-2026年4月-01至07|汇总B·面经03]]
  > [!success]- ✅ AI 解答 · Q87 · 2026-09-23
  > **🎯 标准答案（面试版）**：IoC 把对象的创建与依赖装配从代码里反转给容器：Spring 启动时扫描 @Component 等 BeanDefinition，反射实例化、按构造器/Setter/字段注入依赖，用三级缓存解决单例 setter 循环依赖。AOP 是横向切面：Spring 运行时生成代理对象（有接口用 JDK 动态代理，无接口用 CGLIB 子类），把事务、日志等切面逻辑织入方法调用前后。
  > **📌 要点**
  > - IoC 流程：扫描 BeanDefinition → 反射实例化 → 属性注入 → Aware 回调 → BeanPostProcessor 前后处理 → init → 就绪
  > - 三级缓存：singletonObjects 成品 / earlySingletonObjects 半成品 / singletonFactories 代理工厂
  > - 三级缓存解决 setter 循环依赖；构造器循环依赖无解（Bean 还没实例化无法提前暴露）
  > - AOP 实现：JdkDynamicAopProxy（反射实现接口）vs CglibAopProxy（子类覆写，final 方法失效）
  > - 事务、@Async、缓存注解全是 AOP 的应用层
  > **🔬 原理深入**：为什么用代理而不是直接改字节码继承？代理把横切逻辑与业务解耦、对调用方透明、且能按切点动态匹配。AOP 失效场景的根因也在这里：自调用走 this 而非代理对象，切面自然不生效——这正是 @Transactional 自调用失效的同源问题，两题可以串起来答，体现体系化理解。三级缓存的精妙在于把「提前暴露引用」与「代理延迟生成」解耦：早期引用通过 getEarlyBeanReference 在暴露前才决定是否生成代理。
  > **🔗 延伸**：追问：Bean 生命周期完整链路？为什么需要三级而不是两级缓存？（两级无法同时满足「提前暴露」与「代理语义正确」）
- **是否了解事务注解？注解失效怎么办？** —— `@Transactional` 失效场景：自调用、非 public、异常被吞、传播行为。出处：[[20-Areas/实习与求职/面试题与经验/AI-Agent开发岗位面经汇总-2026年4月-01至07|汇总B·面经02]]
  > [!success]- ✅ AI 解答 · Q88 · 2026-09-23
  > **🎯 标准答案（面试版）**：@Transactional 基于 Spring AOP 代理实现，凡是绕过代理或事务上下文断裂的场景都会失效：①同类自调用（this 调用不走代理）；②非 public 方法；③异常被 try-catch 吞掉；④默认只对 RuntimeException/Error 回滚，受检异常不回滚；⑤传播行为设置不当；⑥多线程调用（事务绑定 ThreadLocal）；⑦存储引擎不支持事务（如 MyISAM）。
  > **📌 要点**
  > - 自调用：拆到两个 Bean、注入自身代理、或 AopContext.currentProxy()
  > - 非 public：代理只增强 public 方法（Spring 6 前）
  > - 异常处理：rollbackFor = Exception.class，或确保异常穿透到代理层
  > - 传播行为：REQUIRES_NEW 挂起外层独立提交；NESTED 用 savepoint 部分回滚
  > - 排查口诀：先看「有没有走代理」，再看「异常有没有到代理」，最后看「回滚规则对不对」
  > **🔬 原理深入**：事务的实现模型是 TransactionInterceptor 在方法前开事务（getConnection + setAutoCommit(false)）并绑定 ThreadLocal，正常返回 commit、抛 RuntimeException/Error 则 rollback。由此反推所有失效场景：「异常被 catch」= 告诉代理一切正常；「同类自调用」= 方法没经过代理这道门；「跨线程」= 事务上下文根本不在同一个 ThreadLocal 里。理解了模型就不用死记条目。
  > **🔗 延伸**：追问：大事务危害？（长持锁、undo 膨胀、连接占用）事务里发 MQ 如何一致？（事务消息 / 本地消息表 / TransactionSynchronization afterCommit）

## 并发与线程池

- **线程池有哪些参数？** —— corePoolSize、maximumPoolSize、keepAlive、队列、拒绝策略。出处：[[20-Areas/实习与求职/面试题与经验/AI-Agent开发岗位面经汇总-2026年4月-01至07|汇总B·面经04]]
  > [!success]- ✅ AI 解答 · Q89 · 2026-09-23
  > **🎯 标准答案（面试版）**：七个参数——corePoolSize（常驻核心线程）、maximumPoolSize（线程上限）、keepAliveTime + unit（非核心线程空闲存活时间）、workQueue（任务队列）、threadFactory（线程创建工厂）、rejectedExecutionHandler（拒绝策略）。核心是执行顺序：先填满 core，满了入队，队列满才扩到 max，再满才触发拒绝——「队列满才建非核心线程」是最反直觉也最常被追问的点。
  > **📌 要点**
  > - 执行顺序：core → queue → max → reject，max 在队列满之后才生效
  > - 队列选型：有界 ArrayBlockingQueue 防 OOM；无界 LinkedBlockingQueue 会让 max 形同虚设
  > - 拒绝策略：AbortPolicy（抛异常）/ CallerRunsPolicy（调用者执行，天然背压）/ Discard / DiscardOldest
  > - 经验公式：CPU 密集 ≈ N+1；I/O 密集 ≈ N*(1 + 等待/计算)，实测压测为准
  > - 生产实践：禁用 Executors 快捷方法，显式 new ThreadPoolExecutor + 有界队列 + 监控
  > **🔬 原理深入**：为什么顺序是 core→queue→max？设计者优先复用已建线程、以队列削峰，把「扩线程」留作队列扛不住时的兜底。这正是 Executors.newFixedThreadPool 用无界队列导致 maxPoolSize 永不生效、任务堆积直至 OOM 的根源。CallerRunsPolicy 的价值在于反压：让提交者自己执行任务，提交速率天然被消费速率约束，是轻量级流控。
  > **🔗 延伸**：追问：动态调参？（setCorePoolSize/setMaximumPoolSize 运行时可改，配监控做弹性线程池）优雅关闭？（shutdown 停接新任务跑完存量 vs shutdownNow 中断 + awaitTermination 等待）
- **给定参数时，如何计算正在运行的线程数？** —— 线程池生命周期与状态推断。出处：[[20-Areas/实习与求职/面试题与经验/AI-Agent开发岗位面经汇总-2026年4月-01至07|汇总B·面经04]]
  > [!success]- ✅ AI 解答 · Q90 · 2026-09-23
  > **🎯 标准答案（面试版）**：这题考 ThreadPoolExecutor 的 ctl 设计。线程池用一个 AtomicInteger 同时编码运行状态（高 3 位 runState）与工作线程数（低 29 位 workerCount），运行中线程数 = ctl & COUNT_MASK，对外可用 getActiveCount() 近似查询。行为上按「core → 队列 → max」顺序：突发 N 个任务时，min(N, core) 个线程立即执行，超出部分排队，队列满后线程数才继续增长到 max。
  > **📌 要点**
  > - ctl = (runState << COUNT_BITS) | workerCount，一次 CAS 同时原子地管状态与计数
  > - getActiveCount() 是近似值（遍历 worker，无锁快照）
  > - 计算题套路：按 core → 队列容量 → max 顺序逐段吸收任务数，得出线程数与拒绝数
  > - 区分 getActiveCount（正在干活）与 getPoolSize（存活 worker，含空闲核心）
  > **🔬 原理深入**：为什么把两个变量塞进一个 int？workerCount 的增减与 runState 翻转（如 shutdown）必须在同一原子变量上完成，拆成两个变量就需要额外锁来维持一致性。COUNT_BITS = Integer.SIZE - 3 = 29，容量上限约 5.4 亿。worker 线程的退出时机也由此驱动：非核心线程空闲超 keepAliveTime、或 allowCoreThreadTimeOut(true) 时核心也可退出，shutdown 时队列清空后全部退出。
  > **🔗 延伸**：追问：给 core=2、max=5、队列=10，提交 20 个任务，线程数与拒绝数各多少？（2 立即跑、10 进队、3 个扩到 max 跑、剩 5 个触发拒绝策略——AbortPolicy 直接抛 RejectedExecutionException）
- **I/O 密集型任务占 90%，四核机器如何配置核心线程数？** —— N*(1+等待/计算) 公式，I/O 密集可远超核数。出处：[[20-Areas/实习与求职/面试题与经验/AI-Agent开发岗位面经汇总-2026年4月-01至07|汇总B·面经04]]
  > [!success]- ✅ AI 解答 · Q91 · 2026-09-24
  > **🎯 标准答案（面试版）**：用经验公式 **线程数 ≈ N × (1 + 等待时间/计算时间)**。I/O 等待占 90%，即 W/C ≈ 9，四核机器约 4 × (1+9) = **40 线程**。这只是起点，实际以压测为准（观察 QPS/RT 拐点微调），并配合有界队列与合适拒绝策略。
  > **📌 要点**
  > - 公式：线程数 ≈ CPU 核数 × (1 + W/C)；I/O 密集可远超核数，CPU 密集约 N+1
  > - 90% I/O 等待 → W/C ≈ 9 → 四核约 40 线程起步
  > - 线程过多的代价：上下文切换、每线程约 1MB 栈内存、调度抖动
  > - 推荐动态线程池：运行时 setCorePoolSize + 监控活跃度/队列深度
  > - Java 21 虚拟线程可从根本上化解 I/O 密集场景的线程数问题
  > **🔬 原理深入**：线程做 I/O 时会释放 CPU，公式的本质是用更多线程填满 CPU 的等待空隙。设任务计算占比 U = C/(C+W)，要打满 4 核需要同时在飞线程 ≈ 4 × (1+W/C)。但收益随线程数递减：上下文切换（寄存器保存恢复、缓存失效）与内存占用线性增长，QPS 先升后降，压测找拐点即可。若用虚拟线程（Loom），阻塞时由 JVM 挂载/卸载载体线程，百万并发只需少量 OS 线程，该公式即失去意义。
  > **🔗 延伸**：常见追问——队列为什么要有界（防 OOM）、四种拒绝策略如何选（CallerRuns + 告警 + 降级）、如何监控线程池；对比 Netty EventLoop 少量线程 + 非阻塞的路线差异。

## JVM

- **JVM 调优时如何查看内存对象情况？有哪些开源工具？** —— jmap、jstat、MAT、Arthas、VisualVM。出处：[[20-Areas/实习与求职/面试题与经验/AI-Agent开发岗位面经汇总-2026年4月-01至07|汇总B·面经05]]
  > [!success]- ✅ AI 解答 · Q92 · 2026-09-24
  > **🎯 标准答案（面试版）**：先用 jstat -gcutil 看 GC 频率与各代趋势，再 jmap -histo 看对象直方图、jmap -dump 导堆快照，用 **MAT** 分析（支配树 + Leak Suspects）；线上推荐 **Arthas**（dashboard / heapdump / vmtool，低侵入），图形化用 VisualVM / JProfiler。配合 -XX:+HeapDumpOnOutOfMemoryError 自动留证。
  > **📌 要点**
  > - jmap：-histo 对象统计、-dump:live 堆快照（注意 STW）
  > - jstat -gcutil：各代容量与 GC 次数/耗时采样，判断晋升过快
  > - MAT：支配树、retained size、GC Roots 引用链定位泄漏
  > - Arthas：在线诊断，dashboard / thread / heapdump 低开销
  > - 容器环境开启 UseContainerSupport，按 MaxRAMPercentage 限堆
  > **🔬 原理深入**：dump 是某时刻堆的对象图快照，MAT 沿 GC Roots 计算每个对象的 retained size（回收它能释放多少内存），排前几名往往就是泄漏源：静态 Map 缓存只进不出、ThreadLocal 未 remove、连接未关闭。jstat 高频采样能看出老年代涨满、Full GC 后不降的模式，这是典型的内存泄漏特征，要与内存不足（调大即可缓解）区分开。
  > **🔗 延伸**：追问路径——频繁 Full GC 怎么排查：jstat 看频率 → dump → MAT 找大对象 → 定位代码；线上 dump 注意先摘流量，大堆 STW 可达秒级。

## MySQL

- **MySQL 索引的数据结构？有哪些种类？** —— B+ 树主键/二级索引、哈希、全文。出处：[[20-Areas/实习与求职/面试题与经验/小红书Agent开发实习生一面-百度Agent面经-杰尼龟|小红书/百度·杰尼龟]]
  > [!success]- ✅ AI 解答 · Q93 · 2026-09-24
  > **🎯 标准答案（面试版）**：InnoDB 以 **B+ 树**为主索引结构：主键聚簇索引叶子存整行，二级索引叶子存主键需回表；另有自适应哈希索引（AHI，引擎自动管理）、FULLTEXT 全文索引（倒排）、空间索引（R-Tree）。按分类说：主键/二级、唯一/普通/联合索引、聚簇/非聚簇。
  > **📌 要点**
  > - B+ 树：非叶子只存键，叶子存数据 + 双向链表，利于范围扫描
  > - 二级索引查非索引列要回表；联合索引满足覆盖即可免回表
  > - 自适应哈希：热点页等值查询自动加速，不支持范围
  > - 唯一索引有唯一性约束；联合索引遵循最左前缀
  > - 8.0 新增：降序索引、函数索引、隐藏索引
  > **🔬 原理深入**：页 16KB，假设主键 bigint 8B + 页指针 6B，非叶子节点扇出约 1170；三层 B+ 树可容纳约 2000 万行量级，这就是两千万行分表经验的来源（层高从 3 涨到 4，每次查询多一次磁盘 IO）。二级索引用主键回表的原因：数据只有一份在聚簇索引，行更新时无需同步多份副本。MyISAM 也是 B+ 树但叶子存数据地址，属于非聚簇。
  > **🔗 延伸**：追问——为什么不用红黑树/跳表：树高由磁盘 IO 决定，二叉树层高爆炸；跳表在内存场景优秀（Redis zset、LSM memtable）。哈希索引为什么不做默认：无序，范围查询与排序全废。
- **B+ 树和 B 树的区别是什么？** —— 数据只在叶子、叶子链表、范围查询优势。出处：[[20-Areas/实习与求职/面试题与经验/小红书Agent开发实习生一面-百度Agent面经-杰尼龟|小红书/百度·杰尼龟]]
  > [!success]- ✅ AI 解答 · Q94 · 2026-09-24
  > **🎯 标准答案（面试版）**：三点区别——① B 树每个节点都存键+数据，B+ 树非叶子只存键、数据全部在叶子；② B+ 树叶子间有双向链表，范围查询与遍历顺链表扫即可，B 树要中序回溯；③ 因此 B+ 树非叶子节点能存更多键，**扇出更大、树更矮、磁盘 IO 更少**，且查询路径等长更稳定。
  > **📌 要点**
  > - 数据位置：B 树内节点+叶子都存，B+ 树只存叶子
  > - B+ 树叶子链表 → 范围查询 / 全表扫天然高效
  > - 扇出：B+ 树内节点无数据，单页容纳更多键，树更矮
  > - 稳定性：B+ 树任何查询都走到叶子，性能可预期
  > - B 树优势：热数据命中内节点即返回，单点查询理论更快
  > **🔬 原理深入**：用数字感受——16KB 页里，B+ 树内节点每条目约 14B（bigint 键 + 6B 指针），扇出约 1170；B 树若内节点再带 1KB 行数据，扇出骤降到约 16，存 2000 万行需要 4~5 层，而 B+ 树 3 层即可，每次层高 +1 = 一次随机磁盘 IO。范围查询方面，B+ 树定位起点后沿叶子链表顺序读（配合磁盘预读近乎顺序 IO），B 树则要反复在树中爬上爬下。
  > **🔗 延伸**：追问——MongoDB 的 WiredTiger 实际也是 B+ 树变体，文档模型单文档命中即返回，不依赖叶子链表做范围扫；与 LSM-Tree 的取舍（写优化 vs 读优化，RocksDB 场景）。
- **MySQL 中乐观锁、悲观锁的使用场景？** —— 冲突率决定选型；版本号 vs `for update`。出处：[[20-Areas/实习与求职/面试题与经验/小红书Agent开发实习生一面-百度Agent面经-杰尼龟|小红书/百度·杰尼龟]]
  > [!success]- ✅ AI 解答 · Q95 · 2026-09-24
  > **🎯 标准答案（面试版）**：**悲观锁**假定冲突常见，读数据时就加锁：select ... for update（排他锁）/ lock in share mode（共享锁），适合冲突率高、临界区短的场景，如库存扣减、余额变更。**乐观锁**不加数据库锁，提交时校验：version 版本号字段或条件更新（update t set stock=stock-1 where id=? and stock>0），受影响行数为 0 即冲突，适合读多写少、冲突率低的场景。
  > **📌 要点**
  > - 选型核心是冲突率：高冲突悲观、低冲突乐观
  > - 悲观锁：for update 需走索引，否则锁住全表扫描行
  > - 乐观锁：version 单调递增防 ABA；失败要重试或报错
  > - 乐观锁无死锁问题，但高冲突下重试风暴反而更差
  > - 秒杀常见组合：Redis 预扣减 + DB 乐观锁兜底
  > **🔬 原理深入**：InnoDB 行锁实际加在索引记录上：for update 走主键/唯一索引锁单行；普通索引在 RR 下还会加间隙锁；无索引则全表扫描的每一行都加 X 锁，效果等同锁全表。乐观锁本质是应用层 CAS：把检查与更新合并进一条原子 UPDATE，依赖 InnoDB 单行写的原子性；ABA 问题用 version 单调递增解决。注意 for update 的锁在事务提交/回滚时才释放，包在长事务里会放大锁竞争。
  > **🔗 延伸**：追问——乐观锁重试几次合适（看业务容忍度，通常 3 次后退化为失败提示）；分布式下两者对应的 Redis setnx / 版本号方案；RR 与 RC 隔离级别对加锁范围的影响。
- **什么情况下加表锁，什么情况下不会加行锁？（原句语境待核实）** —— 锁升级、无索引全表扫描。出处：[[20-Areas/实习与求职/面试题与经验/小红书Agent开发实习生一面-百度Agent面经-杰尼龟|小红书/百度·杰尼龟]]
  > [!success]- ✅ AI 解答 · Q96 · 2026-09-24
  > **🎯 标准答案（面试版）**：InnoDB 是行锁引擎，正常情况下走索引的增删改加行锁；真正加表锁的情况：显式 LOCK TABLES、MyISAM 引擎、DDL 的元数据锁（MDL）。最容易踩的坑是：**update/delete 的 where 条件无索引可用时走全表扫描，所有扫过的行都被加锁——效果等同表锁**。另有意向锁（IS/IX）是表级，但只作行锁的协调标记，不阻塞正常行操作。
  > **📌 要点**
  > - 无索引条件更新 → 全表扫描逐行加锁，并发雪崩（高频事故）
  > - MyISAM 只有表锁；InnoDB 才有行锁
  > - DDL 加 MDL 写锁：长事务未提交会阻塞 DDL，DDL 又阻塞后续所有查询
  > - 意向锁 IS/IX：表级标记，用于快速判断表中是否有行锁
  > - AUTO-INC 锁：自增主键批量插入时短暂持有
  > **🔬 原理深入**：行锁锁的是索引项，这是理解一切的钥匙：update t set x=1 where name='a' 且 name 无索引 → 优化器只能全表扫 → 聚簇索引每一行都加 X 锁（RR 下还有间隙锁），其他会话更新任何一行都被阻塞。解法：给过滤字段建索引，或缩小事务。MDL 经典事故：一个未提交的慢查询持有 MDL 读锁 → ALTER 申请 MDL 写锁排队 → 后续所有 select 都排在写锁后面，整表不可读写。
  > **🔗 延伸**：排查工具——8.0 用 performance_schema.data_locks / data_lock_waits（旧版 innodb_lock_waits）+ show processlist；DDL 安全实践：online DDL、gh-ost/pt-osc、改表前查 information_schema.innodb_trx。
- **结合项目表字段举例，MySQL 如何查询更优？** —— 索引设计、覆盖索引、慢查询分析。出处：[[20-Areas/实习与求职/面试题与经验/AI-Agent开发岗位面经汇总-2026年4月-01至07|汇总B·面经04]]
  > [!success]- ✅ AI 解答 · Q97 · 2026-09-24
  > **🎯 标准答案（面试版）**：拿用户订单表举例：order(id, user_id, status, amount, created_at)，高频查询为查某用户最近订单——建联合索引 **(user_id, created_at)**：等值列在前排序列在后，索引序即排序序，免 filesort；列表页只查所需列实现覆盖索引免回表。深分页用游标（where id < last_id order by id desc limit 10）替代 limit offset。全程用 explain 验证 type/key/rows/Extra。
  > **📌 要点**
  > - 联合索引列序：等值在前、范围/排序在后（最左前缀）
  > - 覆盖索引免回表；拒绝 select *
  > - 索引失效三件套：函数包裹列、隐式类型转换、前导 % like
  > - 深分页：游标法或延迟关联（先查 id 再回表）
  > - explain 关注 type≥range、rows 数量、Extra 无 Using filesort/temporary
  > **🔬 原理深入**：逐层推演：select * from `order` where user_id=123 order by created_at desc limit 10，若只有单列 user_id 索引：先索引找该用户全部主键 → 逐条回表 → 内存 filesort；建 (user_id, created_at) 后索引天然按 created_at 有序，取 10 条即返回。深分页 limit 100000,10 要扫过并回表 10 万零 10 行，游标法直接从上次位置继续，代价 O(page_size)。隐式转换坑：phone 是 varchar，where phone=13800001234 会把索引列当函数计算，直接失效。
  > **🔗 延伸**：追问——索引是不是越多越好：每个索引都是一棵要维护的 B+ 树，写放大 + 优化器误选风险；统计信息过期走错索引：analyze table / force index / 8.0 隐藏索引灰度下线。

## Redis 与网络

- **TCP 的握手与挥手。** —— 三次握手四次挥手、状态机、TIME_WAIT。出处：[[20-Areas/实习与求职/面试题与经验/AI-Agent开发岗位面经汇总-2026年4月-01至07|汇总B·面经03]]
  > [!success]- ✅ AI 解答 · Q98 · 2026-09-24
  > **🎯 标准答案（面试版）**：**三次握手**建立连接：① 客户端发 SYN（seq=x）→ ② 服务端回 SYN+ACK（seq=y, ack=x+1）→ ③ 客户端回 ACK（ack=y+1）。**四次挥手**断开：主动方 FIN → 被动方 ACK →（被动方处理完数据）被动方 FIN → 主动方 ACK，主动方进入 TIME_WAIT 等 2MSL 后 CLOSED。
  > **📌 要点**
  > - 三次握手本质：双方各确认收发能力 + 同步初始序列号（ISN）
  > - 两次握手不行：历史重复 SYN 会误建连接浪费资源
  > - 四次挥手：TCP 全双工，两方向独立关闭，被动方 ACK 与 FIN 分开
  > - TIME_WAIT 只在主动关闭方：等 2MSL，保证最后 ACK 丢失可重发 + 旧报文消亡
  > - 大量 CLOSE_WAIT = 应用忘记 close；大量 TIME_WAIT = 频繁短连接
  > **🔬 原理深入**：为什么握手要三次：若两次，一个迟到的历史 SYN 会让服务端误开连接并占住资源；第三次 ACK 允许捎带应用数据（TFO 基于此）。TIME_WAIT 2MSL 双重职责：① 最后一个 ACK 若丢失，对方重传 FIN 时本端还在，可补 ACK；② 让本连接所有报文在网络中自然死亡，避免污染复用相同四元组的新连接。工程影响：客户端高频短连接打满临时端口（ip_local_port_range 约 3 万个）与服务端 accept 队列溢出，优化方向是长连接/连接池、SO_REUSEADDR、tcp_tw_reuse（需时间戳）。
  > **🔗 延伸**：追问——SYN Flood 与 syncookie（无连接资源占用的编码应答）；握手阶段能否携带数据；四次挥手为何不能合并成三次（被动方可能还有数据要发，ACK 与 FIN 之间是应用层决策）。

# 从指定文件提取知识节点

本命令只处理 `$ARGUMENTS` 中明确给出的文件。它不扫描整个仓库，不根据目录自动扩大输入范围，也不修改来源文件。

## 使用方式

路径都相对于知识库根目录。多个路径用换行或分号分隔；路径含空格时用引号包住。例如：

```text
/BuildKnowledgeNodes 30-Resources/Tech/PTC.md
/BuildKnowledgeNodes 30-Resources/Tech/PTC.md 20-Areas/实习与求职/面试题与经验/小红书-Agent开发实习生-一面面经.md
/BuildKnowledgeNodes "30-Resources/AI/Agent/长时运行 Agent 的有效 Harness.md"; "30-Resources/Tech/PTC.md"
```

参数为空、路径不存在或参数指向的不是 Markdown 文件时，报告问题并停止。不要自行扫描其他文件。

## 每次运行先读的规则

| 文件 | 用途 |
| --- | --- |
| `50-Maps/KnowledgeMapRule/知识图谱框架.md` | 流程、目录和图谱范围 |
| `50-Maps/KnowledgeMapRule/本体登记.md` | 节点类型、关系、字段和约束 |
| `50-Maps/KnowledgeMapRule/知识词表.md` | `domain` 和 `topic/*` 的允许值 |
| `_Templates/概念.md` | 正式节点的 frontmatter 结构 |
| `50-Maps/KnowledgeMap/` | 已有节点，用于消歧和去重；目录不存在时视为空 |

## 阶段一：读取和分类

对每个指定文件读取 frontmatter、标题、正文和已有内部链接，然后给出分类：

- `article`：`source-note`、`book-note`、`paper-note` 或文章资料。
- `interview`：`interview-experience`、`question-bank` 或面试题与经验文件。
- `other`：MOC、项目、岗位、模板等。`other` 文件不抽取知识事实，只报告为已跳过。

路径和 `type` 只是分类线索；两者冲突时，说明冲突并以正文结构为准，不静默猜测。

## 阶段二：分别抽取

### 文章分支

从文章中提取值得独立复用的候选：

- `concept`：概念、机制、现象、术语和理解框架。
- `method`：可复用的方法、算法、流程或模式。
- `entity`：具体的工具、系统、论文、组织或标准。

每个候选必须包含：规范名、建议类型、建议 `domain`、一句话定义、原文证据、证据所在标题、候选关系和不确定项。

不要把文章里的每个名词都建成节点。候选至少应当满足“可能被另一篇笔记引用”或“可能成为一次查询的起点”其中一项。

### 面经分支

面经首先被视为应用场景和考察证据，不把面试者的回答直接当成知识事实。分别记录：

- 面试问题原文。
- 问题考察的已有或候选节点。
- 面试者回答中可以验证的主张。
- 需要其他来源确认的主张。

面经候选必须标注 `evidence_type`：`question`、`candidate_answer` 或 `interview_observation`。题目本身可以连接已有节点，但不因为“被问过”就自动创建一个概念节点。

## 阶段三：对齐和去重

对每个候选读取 `50-Maps/KnowledgeMap/` 中已有节点，并按以下顺序处理：

1. 命中显示名或 `aliases`：复用已有节点，提出补充来源和证据的建议。
2. 只是同义写法：提出加入 `aliases` 的建议，只使用来源中真实出现过的写法。
3. 与已有节点有上下位关系：分别提出 `broader_than` 或 `instantiates`，不要合并。
4. 无法判断是否同一对象：进入“待人工消歧”，不新建也不合并。
5. 确认是新节点：提出新建建议，ID 使用 `node:<规范名>`。

关系只使用 [[本体登记]] v0.1 中登记的关系。只写直接关系，不写传递闭包，也不重复写 `related` 的反向边。

## 阶段四：生成审核报告

首次运行只允许写入：

```text
tmp/knowledge-graph/review/<批次名>.md
```

`<批次名>` 使用指定文件名拼接得到，多个文件之间用 `__` 连接；同一批次重复运行时覆盖旧报告。

报告必须包含：

```markdown
---
type: kg-review
status: pending
sources:
  - "[[来源文件]]"
---

# 知识图谱候选审核：<批次名>

## 文件分类

## 建议新建节点

## 建议补充已有节点

## 面经考察映射

## 待人工消歧

## 待建目标

## 被排除的内容
```

每个候选都要带来源内部链接和真实标题锚点，例如 `[[PTC#两种模式的根本区别]]`。找不到标题时报告错误，不编造锚点。

阶段一结束后必须停下，向用户报告审核文件路径、候选数量和主要不确定项。此时不要创建 `50-Maps/KnowledgeMap/` 中的正式节点，不要修改来源笔记，不要更新 MOC。

## 阶段五：用户确认后的写入

只有用户明确确认审核报告中的哪些候选可以写入后，才执行以下动作：

1. 创建 `50-Maps/KnowledgeMap/`（如不存在）。
2. 按 `_Templates/概念.md` 创建或更新批准的节点。
3. 对已有节点只补充批准的 `sources`、`aliases`、正文证据和关系。
4. 对面经只写入已确认的知识映射，不把未经验证的回答写成定义。
5. 必要时在对应 `50-Maps/` MOC 增加入口。
6. 再运行现有校验脚本；校验脚本与 v0.1 本体不一致时，先报告并修正脚本，不放宽本体规则。

未经确认的候选继续保留在审核报告中，状态仍为 `pending`。本命令不自动提交或推送 Git。

## 质量要求

- 每条候选定义必须脱离来源上下文独立成立。
- 每条关系和每个重要断言都要能回到指定文件中的真实标题。
- “被面试问过”只能证明它是考察主题，不能单独证明答案正确。
- 不因为候选数量少而强行补建节点；宁可保留在“被排除的内容”或“待人工消歧”。
